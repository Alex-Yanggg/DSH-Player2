# Advocate: hand-written behavior trees / finite state machines (advocate-fsm)

## Claim

The perception→action loop for a delegated goal should be owned by a **hand-authored behavior tree (BT), executed by a small deterministic runtime inside the plugin**, against the same body port that `body_walk_to` uses today. The LLM keeps the jobs it is good at — turning the player's words into a DSH goal, choosing and parameterizing a behavior, narrating results, and handling anything the behavior library does not cover — but once a goal is dispatched, ticks, reflexes, retries, and interrupts are fixed code with zero model calls in the loop. This is not nostalgia; it is the only candidate architecture with twenty years of shipped-game evidence (Halo 2/3, Spore, Bioshock-era AAA and since), a production track record outside games (ROS 2 Nav2 runs robot fleets on BTs), mature tooling (BehaviorTree.CPP + Groot2, Unity Behavior, LimboAI), and a property no rival can offer at any price: the executable is a **statically auditable artifact** whose every possible input press, stop condition, and permission check can be enumerated before the companion ever moves — which is exactly what a "trustworthy co-op player, not a bot" requires. Extensibility across games, the judge's top criterion, is a real but bounded per-game cost (a leaf-node pack plus tree data files), carried by a game-agnostic engine and a cross-game node taxonomy — the same economics every studio already pays per title, and the opposite of the per-run model latency and unauditable improvisation the LLM-in-the-loop approaches pay forever. My position concedes one thing up front: a fixed tree cannot invent behavior for goals nobody wrote nodes for. The answer is not to put the model in the tick loop; it is a layered mind (Halo 3 did exactly this: declarative objectives above BTs), where open-ended understanding stays with the model and bounded, delegated execution is code.

## Mechanism

The architecture has three layers, mirroring Halo 3's (objectives → tasks → behavior trees, per Isla's GDC 2008 talk):

1. **Goal intake (LLM, 1 call).** Player says "plant and water the parsnips" in chat. The model calls `body_run_behavior("farm.plant_water", { crop: "Parsnip", near: "player" })` and/or creates the DSH goal. The model's job ends there until narration.
2. **Behavior pack (per-game, fixed code + data).** A library of leaf nodes written against `BodyPort` — conditions (`HasItem`, `StaminaAbove`, `MonsterWithin`, `HealthBelow`), actions (`GotoTile`/`GotoAdjacent` wrapping the existing `walkTo`, `SelectSlot`, `UseOnFacing` for hoe/watering-can/weapon via `ControllerX`, `InteractOnFacing` via `ControllerA`) — plus tree definitions as data files (the BT-as-data form used by BehaviorTree.CPP's runtime-loaded XML and Unity Behavior graphs).
3. **Runner (game-agnostic, in-process).** Ticks the tree whenever a new `BodyState` snapshot or task-status callback arrives. Each action node submits one `BodyTask` (`steps` + `until`) and awaits its status; statuses map to SUCCESS/FAILURE/RUNNING. `until` conditions (`monsterWithin`, `blockedMs`, `arrive`, `warped`) make the adapter itself the interrupt source, so reflexes fire at adapter cadence with `fastState` on — no model in the loop.

**"Plant and water the parsnips" (farm scenario).**

- Root: `Sequence[ GuardPreconditions, SelectPlot, ForEachTile( TileRoutine ), Report ]`.
- `GuardPreconditions` (a Selector with informative failures): has Parsnip Seeds? hoe? watering can? stamina above threshold? A missing precondition fails the tree with a typed reason; the LLM narrates ("I have no seeds left") or dispatches a different tree (`shop.buy_seeds` over the counter/menu nodes).
- `SelectPlot` reads one `world_state` snapshot, picks N tillable tiles (`.` legend chars with no blocking object) in a deterministic order near the player, writes the tile list to the tree's blackboard. The tree stays tiny; the *data* (tile list) carries the combinatorics.
- `ForEachTile`: `Sequence[ GotoAdjacent(tile), SelectSlot(hoe), UseOnFacing (ControllerX) → dirt created, SelectSlot(seeds), InteractOnFacing (ControllerA) → planted, SelectSlot(can), UseOnFacing (ControllerX) → watered ]`, with a reactive fallback above it: `Selector[ Sequence[ StaminaBelow(threshold) → Failure("tired") ], Sequence[ MonsterWithin(k) → flee-and-report ], TileRoutine ]` re-evaluated on every tick.
- `Report` returns a structured result (`{ tilled: 12, planted: 12, watered: 12, failures: [] }`) → `update_goal` → the model narrates in one more call. **Total model calls: 2.** Everything between is local, deterministic, logged.

**"Get to the ladder" (mine scenario: hostiles, low health).**

- Root is a prioritized Selector (BT's native form for tactics): `Selector[ Sequence[ HealthBelow(t) → RetreatFromThreat → Failure("low-health") ], Sequence[ MonsterWithin(k) → EquipWeapon → FaceMonster → Swing (ControllerX) → BackOff ], Sequence[ LadderVisible → GotoTile(ladder) → InteractOnFacing (ControllerA / warp) ], ExploreNearestBranch ]`.
- Every movement node submits its walk task with `until: { monsterWithin: k }`, so a monster stepping into range interrupts the walk *in the adapter*, and the tree's next tick lands in the combat branch — sub-second reaction with no model round-trip (the loop latency problem that PORTAL's authors call prohibitive for LLM inference).
- The retreat branch deliberately ends the tree as a typed failure. The companion then tells the player it backed off and why; the goal survives paused (pause-holds), and `[resume]` re-arms the tree. No cheat inputs (`cheat: true`) appear in any tree, so the pack is auditable against the cheat switch by inspection.

## How it fits the DSH seams

All seven seams, no new runtime process — the honest statement is at the end.

- **Seam 6 (body port + helper libraries) — the core.** The BT engine and runner are plugin helper libraries exactly like `navigation.ts`/`walk.ts` today: they read `BodyState`/`BodyWorld` and submit `BodyTask`/`BodyCancel` files. Nothing in the adapter changes; the port already provides everything the loop needs (snapshots, task statuses, `until` interrupts, `fastState`).
- **Seam 1 (tools).** One new cancellable tool, `body_run_behavior(name, params)`; cancellation with the caller's turn maps to tree abort → `BodyCancel` → body stands still. The existing `world_observe`/`world_find`/`world_map`/`body_controls`/`body_input` tools remain untouched for the model's manual fallback loop.
- **Seam 5 (DSH goals).** DSH keeps owning goal state/queueing/cancellation: the model creates the goal; the tree's structured result feeds `update_goal`; a cancelled or paused goal cancels/suspends the tree.
- **Seam 3 (turn-flow hooks).** `agent/pre-step` maps `[resume]` to re-arming a paused goal's tree and maps goal rounds to progress reports, the same pattern the dream uses today.
- **Seam 2 (prompt sections).** Guidance text: dispatch a known behavior when one matches; drive raw input manually only for what the library doesn't cover; always narrate results in player words.
- **Seam 4 (setup callback).** At plugin start, load the behavior pack matching the body declaration's `game` id and the tree data files.
- **Seam 7 (local files).** Tree definitions (data), per-game node packs, and tick-level execution logs live under the plugin's bridge directory, player-inspectable like the memory ledger.

**Side runtime?** None. The runner is an in-process library loop driven by the same long-lived plugin process that already holds the mod MCP connection; its timers are the same class of thing `walkTo` legs already use inside a tool call. If a future variant ran trees *between* turns (goal rounds do this naturally today), it still needs no second harness — the loop belongs to the plugin, and DSH keeps goals and cancellation.

## Best evidence

- **Iovino, Scukins, Styrud, Ögren, Smith — "A Survey of Behavior Trees in Robotics and AI"** (https://arxiv.org/html/2005.05842v2): "One of the first papers on BTs describe how they are used to create the AI of the highly popular FPS game Halo 2"; FSMs' "n² possible transitions … turns to a single large monolithic structure that is very complex to debug" while BT control transfer "resembles function calls"; subtrees share one interface for reuse; BTs run Nav2, ABB YuMi assembly cells, KUKA/UR applications. Twenty years from Halo 2 to robot fleets.
- **Nav2 official docs — "Behavior Trees"** (https://docs.nav2.org/rolling/getting_started/navigation_concepts/behavior_trees): production robotics chose BTs over FSMs because "Behavior Trees provide a formal structure for navigation logic" that is "verifiable and validated", with reusable primitives and subtree composition. A shipped, safety-relevant system trusting BTs with the whole control loop.
- **Halo 3 GDC 2008 (Damian Isla), attendee notes** (https://aarmstrong.org/journal/2008/03/02/gdc08-notes-building-a-better-battle-halo-3-ai-objectives): "Behaviour trees are used for the individual AI", under a declarative task/objectives layer — the exact layering I propose (model/objectives decide *what*, trees own *how*). Also honest drawbacks I address below.
- **Chris Hecker's Spore Behavior Tree docs** (https://web.archive.org/web/2024/https://chrishecker.com/My_Liner_Notes_for_Spore/Spore_Behavior_Tree_Docs): shipped-game BT practice — "a library for declaring and ticking Hierarchical Finite State Machines", behaviors with `Activate/Deactivate/Tick`, prioritized deciders with hysteresis, statically declared trees, five levels of debug output. Proof that a small team can author a complete creature-AI BT system as a library.
- **BehaviorTree.CPP** (https://github.com/BehaviorTree/BehaviorTree.CPP, ~4.3k stars, MIT, actively maintained) **+ Groot2** (https://www.behaviortree.dev/groot): a mature open-source engine with runtime-loaded tree definitions, and an IDE with live tree monitoring, log replay, blackboard inspection, and breakpoints — debug tooling a model-in-the-loop architecture simply cannot have.
- **PORTAL, "Agents Play Thousands of 3D Video Games"** (https://arxiv.org/html/2503.13356v1) — *a rival's own paper*: "the inherent latency of LLM inference renders them impractical for real-time applications"; their fix is LLM-authored trees exported as DSL/JSON executed at runtime, "eliminating inference latency during gameplay". The runtime architecture both camps need is mine; the dispute is only who authors the trees (see attacks).
- **Unity Behavior** (https://docs.unity3d.com/Packages/com.unity.behavior@1.0/manual/index.html) and **LimboAI** (https://github.com/limbonaut/limboai, ~3.1k stars): BT authoring is commodity engine tooling in 2026, from Unity's official package to Godot's BT+HSM plugin with a visual debugger — the "tooling" argument for hand-authored trees gets stronger every year.

## Extensibility across games

The judge's criterion, head-on. A fixed-tree architecture pays a **per-game cost**; the question is whether that cost is bounded, linear, and reviewable — and what it buys.

- **What does not carry over (honest):** the leaf nodes bound to a game's vocabulary (object kinds, button ids, mechanics) and the tree data files. Each new game needs a pack. Hecker's Spore docs, Halo 3, and every studio BT since show the cost is real and payable.
- **What carries over untouched:** (1) the **runner/engine** — tick semantics, RUNNING/SUCCESS/FAILURE, reactive fallbacks, retry/decorator library, cancellation, logging, replay — game-agnostic, written once (small; BT.CPP's core is the reference design); (2) the **node taxonomy** — `GotoAdjacent`, `SelectItem`, `UseOnFacing`, `IfCondition`, `WithRetry`, `RetreatFrom` — a cross-game grammar of primitives, per-game implemented against the *already game-normalized* body contract (inputs with roles, map legend, typed objects with `extra`); (3) the **dispatch layer** — goal → behavior name + params is the same LLM-facing surface for every game; (4) the **audit/permission tooling** — input allow-list extraction, tree diffing, tick-log format.
- **The economics:** per game, roughly 10–20 leaf implementations plus data files — the same class of work as the per-game SMAPI adapter the repo already accepts, and the *only* candidate architecture whose porting cost is a reviewed artifact rather than a per-run risk. Nav2's docs describe exactly this product shape: one engine, per-application tree XMLs composed from shared subtree plugins. The Iovino survey's reuse point is decisive here: "each subtree is a natural level of abstraction, with all subtrees sharing the same interface" — libraries accrete (a `ShopBuy` tree written for Stardew's menu ports to any game with menus by swapping leaf implementations).
- **Graceful degradation:** a game with no pack is not a dead companion — the model falls back to today's manual tool loop (the baseline remains a subset of this proposal). Trees make known games fast and auditable; the baseline covers the long tail. No rival architecture composes with the baseline this way; most of them *replace* it.
- **Versus the LLM-authoring rivals** (PORTAL, LLM-BT, code skills): they claim near-zero porting cost but pay (a) per-run latency and token cost forever, (b) a per-game *review* burden that the repo's inspectable-permission rule imposes anyway — you must still read what the model wrote before it presses buttons in a shared world — and (c) nondeterminism in the audited artifact itself. My porting cost is paid once, in code review, producing a fixed thing you can enumerate.

## Latency, trust, and debuggability

- **Latency:** model calls happen only at goal intake and narration (2 per delegated task); ticks, retries, and interrupts are local. Reflexes ride the adapter's own `until` conditions (`monsterWithin`, `blockedMs`) with `fastState` — reaction time is bounded by the game tick, not a model round-trip. The strongest witness for this is PORTAL's own motivation: LLM inference latency is "impractical for real-time applications". A body that shares a world with a live player cannot stand idle mid-swing while a completion resolves.
- **Trust and the permission boundary:** a tree is a closed artifact. Every input id it can press, every stop condition, and every stamina/health/duration limit is enumerable statically, before dispatch; a pack can be machine-checked to contain no `cheat: true` inputs. Permissions become an allow-list of behavior names the player granted; revocation is goal cancellation → `BodyCancel` → stand still; pause-holds fall out for free (a paused world advances no ticks, the tree suspends, `[resume]` re-arms). No prompt-based architecture can make the "it will only ever do these things" promise, because its action set is whatever the model composes next turn.
- **Debuggability:** deterministic policy — the same world-state sequence replays to the same input tasks. Tick logs (node id, status, condition values, task ids and reasons) go under the bridge dir; failure reasons are typed (`blocked`, `tired`, `low-health`, `no-seeds`), not model prose. This is the standard the BT toolchain already set: Groot2 replays recorded transitions and shows RUNNING durations per node; BehaviorTree.CPP ships logging "to visualize, record, replay, and analyze state transitions". When the companion does something wrong, the answer is a log line, not a shrug at a context window.

## A minimal prototype on the sim

Against `sim-adapter.ts` (imported unmodified), in `research/behavior-debate/bench/`:

- A ~300-line game-agnostic BT runtime: `Sequence`/`Selector` (reactive), `Inverter`, `Retry`, `ForEach(tileList)`, blackboard; statuses SUCCESS/FAILURE/RUNNING; abort on signal.
- Sim leaf pack: `GotoTile`/`GotoAdjacent` (wrap the existing `walkTo`), `SelectSlot(i)`, `UseOnFacing` (ControllerX — hoe/watering-can/weapon per the sim's rules), `InteractOnFacing` (ControllerA — plant/harvest/ladder), `IfMonsterWithin`, `IfHealthBelow`, `SwingWeapon`, `RetreatFrom`.
- Tree data: `farm.plant_water` (precondition guard → tillable-tile scan → per-tile routine with stamina/monster fallbacks) and `mine.reach_ladder` (prioritized fallback: low-health retreat → melee → walk to ladder → explore), submitted with `until: { monsterWithin }` so the sim's own interrupt does the reflex test.
- Harness: fixed seeds, ≥10 runs per scenario, a scripted "goal dispatch" (no LLM in the loop; if a real model call is cheap to add, use it only for dispatch and mark which runs used it), metrics per TASK.md: success rate, LLM calls per task (0 in-loop), wall-clock, idle ratio (expected ~0 while a tree is active), stuck/recovery counts, LOC, and the toy2 port diff (engine unchanged; new leaf pack + tree data only — that diff *is* the extensibility argument, measured).
- Optional: dump the tick log and replay one run to demonstrate log-explainability.

## Anticipated attacks and your answers

1. **"The repo's design principle says guide-don't-script; your proposal rewrites the product's constitution."** The principle permits fixed logic "with a stated reason why the model or the harness cannot do it", and I state three. (a) *Reflex latency*: a model turn cannot guarantee a response inside the world's tick budget when a monster closes in; the body port's `until` conditions exist precisely because per-turn control is too slow, and PORTAL — a pro-LLM paper — concedes inference latency is "impractical for real-time applications". (b) *Auditability*: the trust constraint requires enumerating what the companion can do before it moves; model-composed behavior is unauditable by construction. (c) *Replay*: explainability from logs demands a deterministic policy. The layering keeps the principle where it belongs: the model still owns words, goals, memory, judgment, and everything the library doesn't cover — the tree is muscle memory for delegated execution, which is also how Halo 3 split objectives (designer intent) from trees (execution).
2. **"Per-game authoring cost kills extensibility across many games."** The cost is real but bounded, linear, and one-time: engine, node taxonomy, dispatch surface, and audit tooling carry over; per game you implement ~10–20 leaves against an already-normalized contract plus tree data files. This is the same per-game cost class as the SMAPI adapter the repo already accepts — and every shipped game with authored AI pays it (Spore, Halo 3, and every Unreal/Unity title with engine BTs). Meanwhile the LLM-authoring rivals' "zero porting cost" quietly re-imports the cost as per-run review of nondeterministic artifacts: the repo's own permission rules require inspecting what will act in a shared world. And the failure mode is graceful: no pack → today's baseline still works.
3. **"BTs can't handle open-ended player goals ('make the farm pretty', 'help me court Penny')."** Correct, and deliberately so: those goals are *conversation, judgment, and decomposition* — the model's tier — not delegated execution. The model clarifies, proposes, and then decomposes into named, bounded behaviors where leaves exist (move, place, gift-give), or drives the manual tool loop for one-offs. The BT tier claims only what the product actually delegates: bounded, inspectable tasks. Halo 3 put a declarative objectives layer above its BTs for exactly this reason; I put the LLM there. Note the asymmetry: my architecture loses nothing relative to the baseline (the baseline is a subset — the model can always fall back), while pure-BT-only would indeed be too narrow.
4. **"This is just scripted botting with a co-op skin."** The botting risk is a property of *unbounded autonomy*, not of fixed code — and fixed code is the strongest place to enforce the boundary. A tree has hard-coded stop conditions (stamina, health, time, day-end), no cheat inputs by construction, per-behavior player-revocable permissions, pause-holds, and DSH-owned goal cancellation. A prompt-guided loop must *trust the model* to respect all of those every turn; a tree *guarantees* it. If anything, "scripted" is the wrong insult: scripted is what you can verify, and verifiable is what you can trust next to your child's save file.
5. **"BTs suffer combinatorial explosion and authoring hell"** (the classic critique — the Iovino survey notes BTs "must be very large to perform tasks that involve many objects and subtasks"). The explosion only happens if you unroll instances into the tree. We don't: the tree is a fixed, small routine; instance data (tile lists, target ids, thresholds) lives on the blackboard, produced per run from one snapshot — `ForEachTile` over a data list, not a tile per node. This is the same lesson as Halo 3's declarative tasks and Spore's statically-declared trees with defaults ("you only write code that does actual AI work"). Where genuine per-instance *choice* is needed (which tiles, in what order), that choice is a parameter the LLM or a cheap planner supplies at dispatch — the survey itself documents the BT+planner hybrid as the standard resolution, and nothing in my claim forbids it: the hybrid's execution tier is still my tree.
6. **"Determinism is a fantasy in a shared, live world."** The claim is a deterministic *policy*, not a deterministic world: same observed state sequence → same inputs. That is precisely what log-based replay, regression tests, and "explainable from logs" require, and it is achievable regardless of how noisy the player's presence makes the world. Model policies cannot even offer that.
