# Advocate: RL / small learned policies

## Claim

The reactive core of the behavior loop — mapping fast-changing observed state to button choices while the world moves — should be owned by **trained policies: small, goal-conditioned networks shipped as versioned artifacts and called through one stable tool** (`body_skill`), while the LLM keeps everything slow: goal decomposition, skill selection and parameterization, interrupt handling, explanation, and (at dev time, not runtime) reward specification. I am the high-risk advocate and I will say so plainly: nobody should train OpenAI Five in a plugin. But RL is the only architecture on this panel whose competence is *learned rather than enumerated* — DreamerV3 collected Minecraft diamonds from scratch with no human data where prompt-driven and scripted agents have nothing to say, and VPT showed the resulting dexterity ships as a file others reuse. Every rival architecture bottoms out in either a model round-trip (too slow for a monster bearing down on low health) or hand-authored decision code (which the repo's own design principle tells us not to write). My honest scoping: policies win the dexterity tier — navigate under threat, fight, execute precise tool sequences — behind the same permission wrapper as today's A* walking; they do not replace the LLM at the goal tier.

## Mechanism

**Where the checkpoint lives.** Each skill is a directory under the plugin's bridge files (seam 7): `<bridge>/skills/<game>/<skill>/policy.onnx` plus `skill.json` declaring the observation spec, the action→controller-id mapping (by the body protocol's existing `role` vocabulary: up/right/down/left/action), a postcondition predicate, a checkpoint hash, a version, and the training eval summary. Weights are data shipped in-repo like `fixtures/` — PyTorch-exported, run in-process by ONNX Runtime's JavaScript bindings (MIT-licensed; runs PyTorch-exported models, CPU execution, no GPU required for a small policy; https://github.com/microsoft/onnxruntime). **Training never runs in the plugin.** It happens offline at dev time against the sim and headless game instances; what ships is an artifact plus a fixed, inspectable inference wrapper sitting next to `navigation.ts`/`walk.ts` (seam 6). This is the direct answer to "a training loop is a side runtime": there is no side runtime — the loop is a dev-time tool, the artifact is data, inference is a library call. If a future foundation-scale policy ever needs a GPU server, that version is a *separate tool the plugin calls with an inspectable contract* (the BRIEF's allowed framing) — but the default design needs neither.

**Observation and action space.** Obs (per state poll): an egocentric window of `map.rows` legend characters (e.g. 13×13), body px/py/facing/selectedSlot, one-hot toolbar categories (hoe/can/seeds/weapon), stamina and health, relative vectors of nearby `characters` (kind, health) and of the current target, plus small counters (tiles tilled so far). Action: a discrete choice over the adapter's declared controller ids mapped by role, converted by the wrapper into ordinary `body_input` steps (`{hold:[DPadLeft], press:[ControllerA], ms: tickMs}`) — write-once task files, replaceable and cancellable, exactly the protocol the body port already defines. The body task schema's existing `fastState` flag ("ask the adapter for a faster state cadence while this task runs (reflexes)") is precisely the hook the policy loop asks for; on the sim, input is polled every 3 ticks of a 60 Hz tick clock, i.e. ~20 Hz effective — the same rate VPT's agents act at from raw pixels (https://arxiv.org/abs/2206.11795).

**"Plant and water the parsnips", step by step:**
1. Player speech → DSH goal (seam 5, unchanged: DSH owns goal state, queueing, cancellation).
2. The model's turn decomposes it: equip hoe → till 6 tiles in a target rect → plant → water. It calls `body_skill {skill: "till-plot", target: rect, budget: {maxTicks, staminaFloor}}` (seam 1).
3. The wrapper checks the permission envelope (skill allow-listed by the current grant; spatial bound = declared rect in current location; budgets), then arms the loop: at each fast-state poll it builds the obs vector, runs the policy (a sub-millisecond forward pass; VPT-class convolutional agents act at 20 Hz, and these skill nets are far smaller), converts the chosen action into the next input step, and submits/updates the body task.
4. The policy is goal-conditioned and emits its own DONE; the wrapper independently verifies the postcondition (N `kind=dirt` objects with `extra.watered` in the rect) and ends on: postcondition met, budget exhausted, `until` trip (blockedMs, monsterWithin), or turn cancellation. It returns an honest report to the model: tiles done, trace path, termination reason.
5. The model sequences the next skill (`plant-plot`, `water-plot`) the same way, then speaks. No model round-trip occurs *inside* any skill.

**"Get to the ladder" (monsters + low health), step by step:** the model calls `body_skill {skill: "run-and-fight", target: ladder tile, healthFloor}`. Obs adds monster relative positions and health; the policy was trained with reward = arrival, −time, −damage taken, so kiting, jab-retreat spacing, and weapon swings (face + action button) are *learned behaviors*, not branches someone wrote. During the run there is zero LLM latency — this is my core latency win over every LLM-in-the-loop rival. If health crosses the floor or the policy exits without arrival, the wrapper interrupts via the existing `until` machinery and control escalates back to the model turn, which can retreat, call for the player, or re-plan — the persona and permission model stay at the LLM tier.

**What the LLM does:** goal decomposition; choosing and parameterizing skills; reading honest skill reports; interrupt recovery; narration; and — at training time, not runtime — writing the reward code per skill in the Eureka pattern (below).

## How it fits the DSH seams

- **Seam 1 (tools):** two new cancellable tools beside `body_input`: `body_skills` (list the registry: skill name, contract, version, eval summary) and `body_skill` (invoke one with goal parameters and budgets). Both cancel with the caller's turn, like every existing body tool.
- **Seam 2 (prompt sections):** guidance on when a skill beats manual input, how to read skill reports, and that skill failures must be surfaced, never papered over.
- **Seam 3 (turn-flow hooks):** none required beyond today's markers; optionally `[resume]` re-arms interrupted skills under the paused DSH goal.
- **Seam 4 (setup callback):** loads the skill registry from the bridge dir, verifies checkpoint hashes and versions against `skill.json`, disables mismatches loudly.
- **Seam 5 (DSH goals):** unchanged. Goals remain DSH-owned; skills are the actuation tier *beneath* goal rounds.
- **Seam 6 (body port + helper libraries):** the skill runtime is a helper library beside `navigation.ts` — it consumes raw `BodyState` and emits raw `BodyInputStep`s through the existing task/until/cancel protocol. It adds no adapter semantics; the mod stays a pure adapter.
- **Seam 7 (local files):** `<bridge>/skills/**` checkpoints + contracts + per-run obs/action traces (jsonl), same pattern as the memory ledger.

**Separate process or side runtime? Honestly:** training is out of the runtime entirely (dev-time, like any build step — the artifact is committed data). Inference is in-process. Nothing here is a second harness, a daemon, or an owner of agent behavior. The only future variant that would be a process is a model-server tool for a foundation-scale policy, and that is explicitly the BRIEF's "separate tool the plugin calls with an inspectable contract" framing, not a side runtime owning the loop.

## Best evidence

- **DreamerV3** (https://arxiv.org/abs/2301.04104, full text https://arxiv.org/html/2301.04104): the first algorithm to collect diamonds in Minecraft *from scratch, without human data or curricula* — 100M environment steps, a single A100 GPU for 9 days (the paper's own contrast: VPT's diamond result took "720 GPUs for 9 days"), one fixed configuration across 150+ tasks, and >1000% data-efficiency gain over IMPALA/R2D2+ on DMLab at 100M vs 1B steps. Takeaway: learned policies achieve long-horizon dexterity that no prompt or hand-written tree delivers, at a *known, bounded* price.
- **OpenAI VPT** (https://arxiv.org/abs/2206.11795, full text https://ar5iv.labs.arxiv.org/html/2206.11795, weights https://github.com/openai/video-pre-training): ~270k hours of scraped video filtered to ~70k clean hours, IDM-labeled, produced a behavioral prior with zero-shot crafting; RL fine-tuning (PPO, ~1.3M episodes / ~1.4×10^10 frames, KL-anchored to the frozen prior) reached >80% iron pickaxes and ~20% diamond collection — human-level on both (humans: 57%/15%) — and the first non-zero ObtainDiamond-pickaxe success (2.5% vs humans 12%). The IDM needed only ~2k labeled hours, and ablations suggest ~100 hours (~$2,000 of contractor data) may suffice. Takeaway: foundation policies are *shippable artifacts others fine-tune* — exactly the multi-game story.
- **Eureka** (https://arxiv.org/abs/2310.12931): GPT-4-written reward code beat human expert rewards on 83% of 29 tasks (52% average normalized improvement), including the first simulated pen-spinning. Takeaway: the LLM's highest-leverage role in my architecture is *reward specification at training time*, not button-picking at runtime.
- **RAMP / NSAM** (https://arxiv.org/abs/2502.13006, 2025): in Minecraft, combining RL policies with learned action models and numeric planning "solves more problems than several RL baselines" and finds more efficient plans. Takeaway: the 2024-2026 literature is converging on exactly my shape — trained low-level skills under a symbolic/LLM caller — not on either extreme.
- **MineRL retrospectives** (https://arxiv.org/abs/1904.10079, https://arxiv.org/abs/2202.10583): the 60M state-action-pair human dataset, 4-day fixed-hardware training budgets, and the 2021 outcome — diamonds came from the permissive "any solution" track while the restricted track only "progressed" — are my honest counter-evidence: at tight sample budgets, pure RL alone does not clear long-horizon game tasks; imitation data and scoping win. That is why I claim the *skill tier*, not the whole game.
- **OpenAI Five** (https://arxiv.org/abs/1912.06680): the ceiling and the warning — self-play RL consuming batches of ~2M frames every 2 seconds for 10 months, first AI to defeat esports world champions. Takeaway: full-game RL is achievable but absurdly costly; nobody ships this per game, including me.

## Extensibility across games

The judge weights this above all, so head-on: **naive per-game RL training is zero extensibility, and I concede the numbers** — DreamerV3 spent 100M steps and 9 GPU-days for one game's diamond task; VPT's RL phase took 720 GPUs for 9 days by DreamerV3's accounting; OpenAI Five trained for 10 months on fleet-scale throughput. Any proposal that says "train a new policy per game at install time" is dead on arrival. My actual extensibility claim has three load-bearing parts:

1. **The training harness transfers, not the loop code.** What is game-agnostic is everything the plugin ships: `body_skill`, `body_skills`, the registry, the obs-builder *pattern* (legend window + characters + toolbar + controller roles — all already game-neutral vocabulary in `packages/contracts/src/body.ts`), the wrapper with budgets and postconditions, and the trace/replay format. Porting to toy2 is new checkpoints plus reward specs — data and config — while the tool surface and inference wrapper carry over. Rivals porting hand-written trees or modes rewrite *decision code* per game; I retrain *data* per game and keep the contract fixed. The TASK.md porting-cost metric should show my changed-code line count near the floor, with training cost accounted separately and honestly.
2. **Foundation policies are the real multi-game asset.** VPT is the existence proof: one large prior trained once, then fine-tuned cheaply per behavior (BC fine-tuning gave 213× more crafting tables than the zero-shot prior). The strategic path for Player2 is a general "body prior" over the body protocol's neutral obs/action space, with per-game skill heads — not N independent policies. [Speculation, and gated]: the mod already mediates the body's raw state and submitted inputs, so recording state-input traces of the player's own farm and the companion's play would yield imitation data at near-zero marginal cost; this is a player-data decision that sits at the operating model's L2 owner-approval gate, not something I assume.
3. **Skill scope beats world-scale.** MineRL showed full-game RL under sample budgets fails; but gridworld-scale verbs (navigate, retreat, engage, till-a-rect) have short reward cycles and tiny state spaces where even modest training converges — that is the shippable subset. For those verbs, a trained policy also *degrades more gracefully than hand-written reflexes* when a game's monsters or terrain behave differently than the author imagined, because competence came from interaction, not from the author's imagination.

Net position for the judge: RL maximizes extensibility *of the shipped artifact surface* (one stable tool, per-game data) while paying in per-game compute at dev time — and for the reactive tier specifically, it is the only candidate whose per-game port is measured in training runs rather than in re-authored decision logic.

## Latency, trust, and debuggability

**Latency — the win.** A skill forward pass is a small matrix multiply in-process: no network, no model round-trip, no queue. The alternative architectures either embed the LLM in the reactive loop (visible idle time while a monster closes) or embed authored code that is fast but blind to anything its author didn't enumerate. VPT-class agents sustain 20 Hz control from raw pixels; my skill nets are smaller than that. During "get to the ladder", the body never waits on a model.

**Trust — the boundary sits outside the policy, by construction.** A policy has no inspectable reasoning, so it must never be the thing that holds permission. Enforcement sits in the fixed wrapper and the existing protocol: skill allow-list per permission grant; spatial bounds (location + rect); time/stamina budgets; adapter-side `until` conditions (monsterWithin, blockedMs) unchanged; cheat inputs still refused by the adapter itself; `body_skill` cancellable with the caller's turn exactly like `body_input`. The policy proposes; the wrapper, the adapter, and the player's grant dispose. This is the same trust posture the repo already accepts for A* walking (opaque search internals; visible bounds, cancellation, and result reporting).

**Debuggability — my real loss, argued honestly.** You cannot ask a policy "why". What can be logged and replayed: every (obs, action) pair per skill run in a jsonl trace; the `skill.json` contract including checkpoint hash, training reward spec, and eval report; termination reason and postcondition check results. Because a skill run is deterministic given checkpoint + obs sequence, a misbehaving run is *reproducible against the artifact* — you can diff what the policy saw. What you lose is verbal explanation at the reflex tier; the LLM narrates intent at the goal tier ("I got to the ladder but I'm badly hurt"), which is also how humans report reflexes ("why did you dodge?" — "I just did"). Where the product requires word-level accountability for an action, that action belongs at the LLM tier, not in a skill.

## A minimal prototype on the sim

- **Trained** (offline, dev-time, against the imported `SimAdapter` — deterministic, keyless, unmodified):
  - `navigate-to`: obs = legend window + goal delta + facing; actions = 4 directions; reward = −Δdistance, arrival bonus; compare wall-clock and stuck count against the existing A* `body_walk_to`.
  - `run-and-fight` (mine scenario): obs += monsters (position/health), own health, ladder direction; actions = 4 moves + face+`ControllerA` swing + retreat; reward = arrival, −damage, −time. Compare against a scripted kiting baseline under the bench's fixed seeds.
  - `till-plant-water`: one goal-conditioned policy with goal tokens (or three small ones); reward = verified dirt/planted/watered counts in a rect.
- **Fixed** (the only shipped code): `body_skill`/`body_skills` tools, registry + checkpoint hash check in the setup callback, obs builder from `BodyState`, wrapper budgets/postconditions/`until` wiring, trace logging, ONNX inference call.
- **LLM**: chooses and parameterizes skills, sequences plant→water, handles `run-and-fight` interruptions (health floor), narrates results; in the bench, a recorded stub stands in for the model and is marked as such.
- **Metrics**: success rate, LLM calls per task, wall clock, idle ratio (should collapse to ~0 inside skills), stuck/recovery count, shipped LOC (small — weights are data), and porting cost to `toy2` (new checkpoints + obs mapping, zero tool-surface changes).

## Anticipated attacks and your answers

1. **"A policy acting at 60 Hz with no inspectable reasoning breaks the trust product."** Permission never lives in the policy. The wrapper enforces the allow-list, spatial bounds, and budgets; the adapter still refuses cheats and honors `until` and cancel; the tool dies with the caller's turn like every body tool. And per-skill traces log every observation and action, which is *more* machine-checkable evidence than the baseline leaves today — the LLM's chain-of-thought is not currently replayable against a committed artifact either; my traces are.
2. **"Per-game training equals zero extensibility."** Conceded for the naive version, with numbers (9 GPU-days for DreamerV3's single diamond task; 720 GPUs for VPT's RL phase). My answer is the split: the *shipped surface* (tools, contract, obs pattern, wrapper, traces) is game-agnostic and measured near-zero changed lines on a port; the per-game cost is compute on data at dev time, plus the foundation-prior path where one artifact is fine-tuned per game (VPT's 213× BC fine-tuning gain). Rivals pay per game in authored decision code; I pay in training runs — for the reactive tier, training is the cheaper and more generalizable currency.
3. **"Reward hacking in a co-op game is a product incident."** True, and CoastRunners is the canonical scar (a boat looping a lagoon to farm target bonuses instead of racing — https://deepmind.google/blog/specification-gaming-the-flip-side-of-ai-ingenuity). Three mitigations, honestly bounded: (a) skills are scoped to short horizons whose postconditions are *verified in game state* (tiles actually watered), and a failed postcondition surfaces as an error per repo rules — no silent local fallback; (b) rewards for game-state verbs are dense and mechanically checkable, not the open-ended shaped rewards where specification gaming lives; (c) reward code at training time comes from the Eureka pattern with human review of the artifact's eval report before it ships. Anything that can't state a checkable postcondition doesn't get to be a skill.
4. **"Sample inefficiency means you cannot ship this."** For full-game tasks, the MineRL record agrees with you — which is why I ship *artifacts trained once at dev time* (like fixtures, like the trained priors OpenAI literally released under MIT), scoped to gridworld-scale verbs with fast reward cycles, bootstrapped by imitation where data exists. The plugin never trains; it loads. Day one on a new game has zero skills and the baseline LLM loop covers it — my architecture degrades to today's baseline, it does not block on it.
5. **"The design principle says guide, don't script — a trained policy is opaque fixed logic."** Backwards. A policy is the purest available form of "policies and tendencies the model composes": learned behavior, not decision code, and precisely not a behavior tree. The fixed parts (wrapper budgets, bounds) are exactly the principle's "allowed constraints — boundaries, not behavior". The rivals' hand-written reflex layers and authored trees are the fixed decision code the principle warns against; I moved competence out of code and into composable artifacts.
6. **"Why not the modes/utility advocates' hand-tuned reflex layer — same speed, no training?"** Because their competence is bounded by the author's foresight: a hand-tuned engage/retreat threshold is exactly the fixed logic that fails out-of-distribution (new monster speed, mixed packs), whereas a damage-avoidance-trained policy adapted during training. And their layer still needs per-game hand-tuning — which is the extensibility cost they are about to be attacked on — while a policy's per-game cost at least buys behavior that was tested by interaction, with an eval report attached to the artifact.
