# Advocate: GOAP/HTN planners with LLM-produced goals and domains (advocate-goap)

## Claim

The loop that turns "plant and water the parsnips" into button presses should be owned by a fixed classical planner — GOAP (F.E.A.R.-style actions with preconditions/effects over a symbolic world state, searched with A*) or an HTN decomposer — running as an in-process library inside the DSH plugin, while the LLM does the two jobs it is actually good at: translating the player's words into goal predicates and bindings, and authoring/extending the per-game action domain from the adapter's declared vocabulary, under validator feedback. This split is not ideology; it is measured division of labor. LLMs demonstrably cannot reliably do multi-step planning over exact state — LLM+P exists because LLMs alone "cannot reliably solve long-horizon planning problems" and the LLM+PDDL-with-environment-feedback pipeline solves 66% of tasks where GPT-4 with chain-of-thought alone solves 29% (fetched numbers, below) — while a classical planner over grounded predicates is exact, deterministic, millisecond-fast, and free. F.E.A.R. shipped exactly this planner layer in a 2005 real-time shooter, and Orkin's stated reason is ours: not that any single behavior is impossible otherwise, but that "the complexity of the combination and interaction of all of the behaviors becomes unmanageable" any other way. The judge's criterion — extensibility across many games while staying a DSH plugin — is precisely where this architecture wins: the planner core and the execution loop are game-agnostic code shipped once; everything game-specific is *data* (a predicate vocabulary plus an action domain), and the LLM can draft that data from the game adapter's own declaration, with the fixed planner acting as the sound verifier in a Kambhampati-style LLM-Modulo loop. No second harness, no daemon, no new runtime: the planner is a pure function beside `navigation.ts`, called through the same seven seams the plugin already uses.

## Mechanism

The architecture has four fixed pieces and two LLM pieces:

- **Fixed 1 — Grounding:** a small extractor that turns raw `BodyState` (map rows, legend, objects with `kind`/`extra`, characters, warps, toolbar, stamina) into a set of ground predicates. The vocabulary is derived from the adapter's `bodyDeclaration`: the legend record, object kinds seen, state field descriptions, and input roles. Example facts for the sim/Stardew: `tilled(4,7)`, `tile(4,7,dirt)`, `holding(hoe)`, `has_item(parsnip_seeds, slot 2)`, `water_in_can(40)`, `monster_within(3)`, `health_low(true)`, `at(Farm, 4, 6)`, `warp(ladder, 10, 2, Mine, kind=walk)`.
- **Fixed 2 — Domain (data, per game):** a JSON file of actions. Each action = name, parameters, preconditions (predicates), effects (predicate add/delete), cost, and an *operator template* — a recipe for compiling one plan step into body-port work (a `body_walk_to` leg in `adjacent` mode plus `Slot{i}` press plus `ControllerA` press with `until: {blockedMs}` — exactly what `body_input` already accepts).
- **Fixed 3 — Planner:** GOAP-style A* over world states (Orkin's Difference #1: action costs guide A*; the planner searches "states of the world" as nodes, actions as edges), with Orkin's other three pragmatics: fixed-slot world state, *procedural preconditions* (e.g., "a monster-free path exists" checked on demand against the A* nav helper — his exact F.E.A.R. example), and *procedural effects* (the operator that drives the body when the step executes). An HTN variant is a drop-in alternative: compound tasks with ordered methods decompose top-down with backtracking (Humphreys' total-order forward decomposition); I would ship GOAP first because goal predicates come straight out of goal translation, and keep HTN's *method traversal record* idea for replan hysteresis (below).
- **Fixed 4 — Plan runner:** executes steps in order. Before each step it re-derives predicates from a fresh state read and re-checks that step's preconditions (Humphreys' plan-runner validation against a working world state). Steps compile to body task files via the operator templates; guards like `until: {monsterWithin: 2}` are attached per step from the domain. If a remaining precondition is violated, or a step's run ends `interrupted`, the runner replans locally (no model call) and continues; if the goal itself is unreachable, it stops and surfaces to the model.

- **LLM 1 — Goal translation (once per goal, in the normal DSH turn):** the model reads the active DSH goal and the injected predicate vocabulary, and emits goal predicates plus bindings: "plant and water the parsnips" → `∀ t ∈ plot(3..5, 7): planted(t, parsnip) ∧ watered(t)`, `seed_slot = 2`. This is the SayCan division inverted for our setting: the LLM supplies semantics, a fixed mechanism supplies grounding and sequencing.
- **LLM 2 — Domain authoring (rare, per new game/verb):** when the goal needs verbs the domain lacks, the model drafts new actions (predicates from the declared vocabulary only); the draft is validated by schema check, by planner dry-run on recorded states, and by a shadow run on the sim; it is stored as a versioned data file and only then used live.

**"Plant and water the parsnips", end to end.** The player types the sentence; the model creates the DSH goal with the predicate form above. On the goal round, the plan tool runs: grounding produces facts (`tile(x,7,dirt)` for x=3..5, `holding(nothing)`, `has_item(hoe)` …), A* returns, e.g., `SelectSlot(0) → [WalkAdjacent(3,7), UseTool(hoe,3,7)] → [WalkAdjacent(4,7), UseTool(hoe,4,7)] → … → SelectSlot(2) → [WalkAdjacent, UseTool(seeds,…)]×3 → RefillCan → [UseTool(can,…)]×3`. Execution walks legs, swings, verifies `tilled(4,7)` from the next state read before moving on. If the player tilled two tiles themselves mid-plan, the next re-check sees the predicates already true and the runner skips/replans cheaper — GOAP only ever plans for unsatisfied goal literals, so donated progress is absorbed for free. Model calls for the whole task: the goal-translation turn (already needed today) plus zero per-step calls.

**"Get to the ladder" (monsters + low health), end to end.** Goal: `at(ladder_adjacent)` with a standing invariant `alive` (i.e., `health > 0` modeled as a predicate maintained by sensors). The domain contains `WalkLeg(to)` with a *procedural precondition* "path exists" and cost = path length, `Attack(monster)` [pre: `monster_within(1) ∧ holding(sword)`; eff: `threat_cleared`], `Flee(to)` [procedural pre: "monster-free path exists"; cost reduced when `health_low`], `UseWarp/UseLadder` [pre: `at(adjacent)`; eff: `at(ladder_adjacent)`]. A* picks between the short corridor past the monster and the long safe detour *using the cost function that reads health* — exactly Orkin's flee-vs-hunker procedural-precondition pattern. During execution the walk leg carries `until: {monsterWithin: 2}`; a monster closing cancels the input task, the runner re-derives facts (`monster_within(2)` true), remaining-step preconditions are violated, and it replans — insert `Attack` or switch to the `Flee` detour — all in-process, no round trip. Replan hysteresis (Humphreys' MTR idea): the runner only abandons the running plan for a strictly higher-priority/cheaper one, and only replans on violated preconditions, never on every sensor change — that is the documented cure for the "recovery animation aborted by its own success" class of bug.

**Two or three concrete GOAP actions (farm domain):**

```
action TillTile(x, y)
  pre:  tile(x,y, dirt) ∧ ¬tilled(x,y) ∧ standing_adjacent(x,y) ∧ holding(hoe)
  eff:  +tilled(x,y), −stamina_ok if stamina < ε   (cost: 2)
  operator: face(x,y); press ControllerA; until {blockedMs: 500}

action PlantTile(x, y, crop)
  pre:  tilled(x,y) ∧ ¬planted(x,y) ∧ holding(seeds(crop)) ∧ standing_adjacent(x,y)
  eff:  +planted(x,y, crop)                          (cost: 2)
  operator: face(x,y); press ControllerA

action WaterTile(x, y)
  pre:  planted(x,y, _) ∧ ¬watered(x,y) ∧ holding(watering_can) ∧ can_charged
  eff:  +watered(x,y), −can_charged when can_empty  (cost: 2)
  operator: face(x,y); press ControllerA
```

with helper actions `SelectSlot(i)` [+holding(item_in_slot_i)], `WalkAdjacent(x,y)` [+standing_adjacent(x,y), cost = manhattan], `RefillCanAt(water)` [+can_charged]. Goal `planted ∧ watered` over the plot forces the chain till→plant→water per tile via precondition/effect chaining — this is Orkin's "Attack needs WeaponLoaded, Reload supplies WeaponLoaded" chaining, one decade and one genre over.

## How it fits the DSH seams

Uses seams **1, 2, 3, 4, 5, 6, 7** — all seven, none new:

1. **Tools (seam 1):** one new tool family, all turn-cancellable like today's body tools: `plan_prepare` (LLM output of goal predicates/bindings is checked against the vocabulary and echoed back for the model to confirm), `body_execute_plan` (runs the fixed planner and the plan runner; returns per-step verified results), `domain_propose` (LLM drafts actions; runs validator + dry-run; writes a *pending* domain version, never auto-live). No tool is a daemon; each call is a synchronous function.
2. **Prompt sections (seam 2):** a policy section ("state goals as predicates from the declared vocabulary; never invent predicates or buttons; if a needed verb is missing, propose a domain addition") and an injected per-game block listing the predicate vocabulary and known actions, generated from the same domain file the planner uses — one source of truth.
3. **Turn-flow hooks (seam 3):** on goal rounds, `agent/pre-step` injects a compact plan status note (goal predicates met/unmet, current step, last replan and why). `[resume]` after a pause re-checks predicates and continues or replans — pause still holds the goal; DSH keeps owning that.
4. **Setup callback (seam 4):** loads the per-game domain file (seam 7 data), compiles action schemas, initializes the planner and grounding map. Pure initialization, no threads.
5. **DSH goals (seam 5):** unchanged ownership. DSH creates/queues/cancels goals; the model writes the goal text with the predicate form; the plugin only *observes* the active goal and executes its strategy. Preemption between goals (water-my-crops vs survive-the-monster) is DSH's goal priority, not a planner daemon's.
6. **Body port + helper libraries (seam 6):** the planner sits beside `navigation.ts`/`walk.ts` as another helper library the tools call. Its steps *compile down to* `body_walk_to` and `body_input` task files — the adapter still sees nothing but raw buttons, honoring "the mod is a pure adapter."
7. **Local files (seam 7):** `domains/<game>.json` (the per-game data), `domains/pending-*.json` (LLM drafts awaiting validation), and `plans/<goalId>.json` (the inspectable plan artifact: goal predicates, facts snapshot, ordered steps with preconditions, per-step verification results, replan log).

**Honest process answer:** nothing here needs a separate process or side runtime. The planner is a *library*, not a daemon: planning is a pure function `(domain, facts, goal) → plan` with no I/O, no event loop, no long-lived state. At our domain sizes (tens of actions, tens of relevant tiles) A*/DFS runs in well under a millisecond in JS — GTPyhop's entire core is a single Python file (BSD-3-Clause-Clear), and an Excalibur.js hobbyist built a working TS GOAP planner with costs, preconditions/effects, and replanning as a blog-sized project; F.E.A.R. ran this class of search per-agent in 2005 combat. The only "runtime" is DSH itself, which already exists. This is squarely the "helper library the plugin ships" case the brief allows, not the "side tool with an inspectable contract" case — though even `domain_propose`'s validator is also just in-process code.

- **Kambhampati et al., "LLMs Can't Plan, But Can Help Planning in LLM-Modulo Frameworks" (ICML 2024):** https://arxiv.org/abs/2402.01817 — the position paper for exactly my two LLM roles: LLMs as knowledge/model generators inside a loop with external sound verifiers (a classical planner being the verifier).
- **Guan et al., "Leveraging Pre-trained LLMs to Construct and Utilize World Models for Model-based Task Planning" (NeurIPS 2023):** https://arxiv.org/abs/2305.14909 — GPT-4 authored PDDL models for **40+ actions**; corrected domains solved **48 challenging tasks**; corrections come from PDDL validators and humans *once per domain*, not per plan — the validated-database argument for LLM domain authoring.
- **Mahdavi et al., "Leveraging Environment Interaction for Automated PDDL Generation and Planning with LLMs" (NeurIPS 2024):** https://arxiv.org/abs/2407.12979 — environment-feedback refinement of LLM-written domains: **66%** average solve rate over 10 PDDL environments vs **29%** for GPT-4 doing intrinsic chain-of-thought planning — both halves of my claim in one table: domains are authorable-with-feedback, and the LLM alone is the weak planner.

- **Guerrilla Games, "HTN Planning in Decima":** https://www.guerrilla-games.com/read/htn-planning-in-decima — HTN "drives the NPC's high-level decisions" in Killzone and Horizon Zero Dawn/Forbidden West, with Prolog-like backtracking over preconditions and in-game decomposition debugging — planner-as-data at AAA scale, and the debuggability claim.
- **Open-source scale of the fixed core:** https://github.com/dananau/GTPyhop — Dana Nau's maintained HTN+goal planner whose entire core is one Python file, BSD-3-Clause-Clear (plus Run-Lazy-Lookahead integrated planning-and-acting semantics); and https://excaliburjs.com/blog/goal-oriented-action-planning — a TypeScript GOAP planner with costs, precondition/effect chaining, and `cancelPlan()` replanning built as a blog demo. - **PlanBench (Valmeekam et al.):** https://arxiv.org/abs/2206.10498 — benchmark paper whose abstract states LLM performance on plan generation "falls quite short" even for SOTA models; the standing negative result that justifies not letting the model own the search. (Exact solve rates are in the PDF tables, not the fetched page; I cite only the qualitative abstract claim.)

## Extensibility across games

This is the judge's weighted criterion, and it is the architecture's structural argument:

- **All game specificity is data.** The fixed stack (grounding extractor driven by the adapter declaration, planner, plan runner, tools, prompt policy) is written once against the *body protocol*, not against Stardew. Porting to a second game means: (1) a new `domains/<game>.json` — predicates over that game's legend/object kinds, actions whose operator templates use that game's declared buttons; (2) nothing else. The predicate vocabulary is *generated from what the adapter already declares* — `bodyDeclaration` ships a legend record, per-input plain-word descriptions with roles, and state-field descriptions (body.ts). That declaration is the shared vocabulary the LLM translates into and the domain is written over; the same artifact feeds model, domain, and tests.
- **The LLM is the porting tool.** For a new game the model reads the declaration plus a state sample and drafts the domain; the fixed planner validates it (schema; dry-run reachability over recorded states; shadow execution on a sim/bench). Guan et al. showed GPT-4 modeling 40+ actions with validator correction; Mahdavi et al. showed environment-feedback refinement lifting solve rate to 66% vs 29% for intrinsic LLM planning. Domain authoring is a bounded, one-time-per-game, artifact-producing job — exactly the kind of job LLM-Modulo says LLMs are for.
- **Compare the porting cost of rivals on the same axis.** Hand-written BTs/FSMs port by rewriting the whole tree per game. LLM-authored BTs port by re-prompting, but the artifact has no semantics a machine can verify — a BT is executable control flow, not a declarative model; nothing checks it against reality before it runs. Learned policies port by retraining per game. Pure tool-calling ports by writing new tools and longer prompts — and keeps paying the per-step model round-trip. My domain ports as reviewable JSON with a machine-checked contract (every predicate grounded in the declaration; every action's operator compiling to declared buttons; every plan re-checkable by replaying recorded states).
- **Staying a DSH plugin is trivially preserved** because the planner is an in-process library and the game adapter boundary (raw state in, raw buttons out) is untouched — seam 6 exists precisely for helper libraries of this shape (`navigation.ts` is precedent: A* over tiles is already a fixed library the model calls through a tool; I am extending that precedent from *space* to *state*).
- **Domain diff = PR-able data.** New game verbs (fishing, combat combos in another game) are added as new actions in the data file, validated offline; Orkin's drones story is the canonical evidence that adding behavior to a planner means adding data, not editing every existing branch — the exact property "many games" demands.

## Latency, trust, and debuggability

- **Visible latency: plan-then-execute vs model-per-step.** The model is consulted once per goal (translation) and rarely (domain additions); every step between is local planner + state read + button task — the body is never idle waiting on a model round-trip, which is the direct fix for the brief's idle-ratio concern. Replanning under monsters is the case where rivals pay a model call (or stall); here it is a sub-millisecond A* re-run, because the plan was cheap to produce in the first place — F.E.A.R. re-planned individual soldiers in real time in 2005.
- **Trust and the permission boundary: plans are inspectable artifacts before execution.** `plans/<goalId>.json` is written before the first button press: goal predicates, the facts the plan was built on, every step with its preconditions and operator, and then per-step verification results and replan entries appended live. That is a *reviewable, revocable description of intended physical action* — the artifact the "explicit, inspectable, player-revocable permissions" rule wants. A BT or a model's tool-call stream never gives you the intention up front; a plan is the intention, in data, before it happens. Revocation reuses DSH's existing cancel (turn cancellation cascades into body task cancel, which already exists in the tools), and pause-holds-goal semantics are untouched because DSH still owns goals. A plan preview in the F2 overlay ("going to till 3 tiles, plant parsnips, water them — say stop") is one render of that JSON.
- **Log-explainability: deterministic replay.** Misbehavior is explained from logs without a model in the loop: same domain version + same facts snapshot ⇒ same plan. The log answers "why did it swing at that monster" with a *reason* (which precondition of which remaining step was violated, what the cost comparison was), not with a paraphrase of a transformer. Guerrilla built in-game decomposition debugging for exactly this; Humphreys' chapter is explicit that the decomposition is inspectable. The LLM-authored domain, when involved, is itself a small versioned file you can diff — blame attribution has a file boundary.

## A minimal prototype on the sim

Bench prototype in `bench/goap/` (imports `SimAdapter` via the existing `BodyPort`, wrapper scenarios per TASK.md):

- **Fixed code (game-agnostic, ~navigation.ts-sized):** predicate extractor over `BodyState` (legend chars → `tile(x,y,T)`, objects → `tilled/planted/ready/monster_at`, toolbar → `holding/has_item`, `at`, `health_low`); GOAP planner (A* over cloned fact sets, per-action costs, procedural preconditions calling the A* nav helper for path existence); plan runner (per-step precondition re-check, operator compile to `body_input` steps with `until` guards, replan-on-violation with MTR-style hysteresis).
- **Data (per scenario, JSON):** farm domain (`SelectSlot`, `WalkAdjacent`, `TillTile`, `PlantTile`, `WaterTile`, `RefillCan`) over the sim's hoe/watering-can/seeds; mine domain (`WalkLeg`, `AttackSwing` via weapon slot + `ControllerA`, `Flee`, `UseWarp` for the ladder/'W' warp) with monsters that die to a swing and a `health_low` cost modifier.
- **LLM does:** goal translation only — "plant and water the parsnips over rows y=7, x=3..5" → `planted ∧ watered` predicate set + seed slot binding; "get to the ladder, careful, you're hurt" → `at(ladder_adjacent)` with survival invariant. Use a recorded model stub if no live GLM call is wireable from the script, and mark those numbers as stubbed, per TASK.md.
- **Fixed planner does:** everything else — plan search, step execution, verification, replanning.
- **Measured per TASK.md:** success rate over ≥10 seeded runs per scenario; LLM calls per task (target: 1); wall-clock and idle ratio (target: idle only during goal translation turn); stuck/recovery counts (replans per task is the interesting one); non-test LOC split fixed-vs-data; porting cost — point the same fixed stack at `bench/toy2/` by writing only a new domain JSON + legend map and counting changed/added lines (the pitch: the fixed stack should be zero-diff).
- **Extra check worth having:** a domain-validation harness (schema + dry-run plan over recorded states) demonstrating the LLM-domain-authoring loop with a deliberately broken draft that the validator rejects.

## Anticipated attacks and your answers

1. **"LLM-authored domains are where all the difficulty went — you moved the hard part into a step with no guarantees."** Partially fair, and the answer is: that difficulty is *bounded and validated*, which is strictly better than every rival. A domain is written once per game and then machine-checked forever: schema validation (predicates must exist in the declared vocabulary), planner dry-runs (does the domain even admit plans over recorded states?), and shadow execution (do the operators' effects match reality on the sim before going live). Guan et al. measured exactly this loop — 40+ GPT-4-authored actions, validator-corrected, solving 48 tasks — and Mahdavi et al. measured environment-feedback refinement reaching 66% vs 29% for intrinsic planning. The alternative architectures face the same grounding/semantics problem *at every step of every plan* with no verifier anywhere; I face it once per game with a sound one.
2. **"Replanning storms under monsters — the mine scenario will thrash."** This is a solved problem with named solutions: (a) replan triggers are *violated preconditions of remaining steps*, not sensor changes (Humphreys spells out this exact failure mode — a plan aborted because its own successful step changed state — and the fix); (b) priority hysteresis via the method-traversal-record comparison so a running valid plan isn't abandoned for an equal-priority newcomer; (c) monster guards ride the body protocol's `until: monsterWithin`, cancelling input *without* a model call; (d) replan budgets per goal round — after N local replans, stop and surface to the model (which is the trustworthy-co-player behavior anyway: "this isn't working, help"). Orkin's working-memory pattern additionally turns failures into facts (`path_blocked(w)`), so repeated failures inform the next search instead of looping.
3. **"Grounding predicates in raw tiles is the unsolved part — your planner is only as good as facts you don't have."** Every rival needs the identical mapping (a BT's conditions, a utility scorer's inputs, and the baseline model's tool results are all the same facts in different clothes); planners are the only architecture where the mapping is *explicit, typed, and unit-testable* — a fact file you can replay. And the raw material is already declared semantics, not pixels: the adapter ships a legend with per-character meanings, objects with kinds and `extra` payloads, inputs with plain-word descriptions and roles (body.ts). The genuinely open cases (unexported state) fail loudly as missing facts — the repo's own rule of surfacing rather than silently degrading applies, and a missing-fact failure is a precise upstream requirement ("export crop watered state"), not a mystery.
4. **"HTN methods are just BTs in a trench coat — ordered conditional branches with extra steps."** No, and the difference is load-bearing: a BT is control flow over *checks*; an HTN method set is *search* — the decomposer simulates effects forward on a working world state, backtracks when a branch's future preconditions fail, and can produce a different plan from the same methods tomorrow because the world differs. Humphreys again, verbatim in spirit: unlike behavior trees, HTN planners "reason about the effects of possible actions." And the GOAP side is even further from a BT: goals and actions are decoupled, so adding behavior never edits existing behavior — Orkin's flying drones were a new enemy assembled from existing actions late in development, the concrete anti-trench-coat datum. (For the judge: the trench coat runs the other way — a plan is an inspectable artifact a BT never hands you.)
5. **"This violates the repo's design principle: 'guide, don't script' — a planner domain is fixed decision code."** Argued head-on: the principle says fixed logic needs a stated reason the model or harness cannot do it. Here is the stated reason, with evidence: models measurably cannot do reliable multi-step search over exact state (LLM+P's premise; PlanBench's abstract; 29% vs 66% above), while A* over STRIPS actions is a 50-year-old exact solution costing one file of code. What I am *not* fixing is judgment: goal choice, translation, priorities (costs are policy the model can argue with), domain authoring, conversation, and every "should I even do this" call remain the model's. The domain itself is *declarative knowledge* — what tilling requires and causes — which is closer to the "perception, hands, and thinking guidance" triad than a BT is; deleting it doesn't make the companion smarter, it makes it slower and less reliable. And the code-budget rule wins too: the planner replaces per-goal chains of model round-trips with one local function; by the repo's own accounting that deletes fixed interaction logic (the prompt engineering needed to keep a model on-plan) and adds one bounded library.
6. **"Millisecond planning is a fantasy once domains grow; you'll need timeouts, anytime behavior, a planner service."** At realistic domain scale (a game's verbs, not IPC-hard problems) this is contradicted by shipping data: F.E.A.R. planned per-agent in real time in 2005; Fall of Cybertron's HTN was *faster* than its predecessor GOAP; GTPyhop is a single file. If a domain ever grows past comfortable size, the documented mitigations are Humphreys' partial-planning section and goal-size bounding (plan per goal predicate, not per save) — and the worst case degrades to "replan takes 50ms," still invisible next to any model round-trip.
