# Advocate: data-driven reflex/modes layer under the LLM (system 1 + system 2)

## Claim

The behavior loop should be owned by a **fixed, data-driven reflex layer that runs under the LLM**: the model (system 2) keeps what only a model can do — reading the player's words, forming goals, choosing and tuning *policy* — and expresses that policy as a small declarative **mode table** (modes = `f(state predicates, priority)`, each mode bound to a macro over the body port); a deterministic selector loop (system 1) executes between model turns at tick cadence, preempting by priority and reporting interrupts back to the next turn. This is the only split that satisfies all of the brief's constraints *simultaneously* rather than trading them off: reaction latency collapses to the adapter's own `until` conditions and a plugin-side poll (zero model round-trips to not die in the mine), the permission boundary becomes *inspectable data with named, per-mode revoke points* instead of a stream of opaque tool calls, and extensibility across games becomes "author one JSON file in the adapter's declared vocabulary" instead of "port a tree, a domain, or a code generator." Shipped industry evidence points this way: KRAFTON's PUBG Ally runs an on-device SLM for intent and speech over a behavior tree executing at game tick rate, explicitly so that "reflex-level actions never have to wait for the model" ([NVIDIA developer blog](https://developer.nvidia.com/blog/how-krafton-built-pubg-ally-a-co-playable-character-powered-by-nvidia-ace)); Mindcraft ships exactly this shape in open source (priority-ordered modes with interrupt flags, run per tick, with an auto-message to the LLM when one fires — [modes.js](https://raw.githubusercontent.com/mindcraft-bots/mindcraft/develop/src/agent/modes.js)); and the ACL 2025 DPT-Agent shows a fast FSM/code-as-policy system 1 under an LLM system 2 is what finally makes *real-time simultaneous human-AI collaboration* work ([arXiv:2502.11882](https://arxiv.org/abs/2502.11882)). The repo already agrees in principle: `README.md` places "navigation and reflexes" in the plugin, and `packages/contracts/src/body.ts` ships the substrate — `until` conditions and a `fastState` flag whose own comment says "reflexes."

## Mechanism

The runtime has three latency tiers, one per layer:

1. **Adapter tier (game tick, zero round-trips).** Every submitted task carries `until: { arrive | blockedMs | monsterWithin | warped }` (`packages/contracts/src/body.ts`, `bodyUntilSchema`) with `fastState: true`. The *game process itself* stops the body the instant a monster closes inside `monsterWithin` tiles and reports `interrupted / "monster"`. This is Brooks' "the world is its own best model" ([subsumption architecture](https://en.wikipedia.org/wiki/Subsumption_architecture)) made contractual: no representation, no polling lag, the world is the tripwire.
2. **Reflex tier (plugin poll, ~100–250 ms).** A fixed `ModeSelector` timer inside the plugin process polls state (at `fastState` cadence while a task runs), evaluates the mode table top-down by priority, and lets the winner submit/replace the body task. Modes may `interrupts: "all"` (survival) or never interrupt. This is Mindcraft's `ModeController.update()` shape: iterate in priority order, first active mode wins, break ([modes.js](https://raw.githubusercontent.com/mindcraft-bots/mindcraft/develop/src/agent/modes.js)).
3. **Model tier (DSH turns, seconds).** The LLM does goals, words, and policy: it picks modes, sets params, and reads the digest of what the lower tiers did between its turns.

**"Plant and water the parsnips."**

1. Player words → plugin feeds a DSH goal (seam 5): `create_goal("plant and water the parsnips")`. Goal round begins; `agent/pre-step` (seam 3) injects a body-status section: current location, toolbar, plot candidates, active modes.
2. Model turn (system 2): `world_find(kind: "dirt")`, `body_controls` to learn the toolbar, then one call to a new tool `modes_set` — activate `field_work` with params `{plot: 12..16 × 8..10, steps: [till, plant:"Parsnip", water]}` and bind it to the active goal. One or two model calls, then the model's turn ends.
3. Between turns, the selector executes `field_work`'s macro: for each tile in the plot, plan a leg with the existing A* helper (`navigation.ts`), `body_walk_to`-style macro submits `{hold: [DPadRight], ms}` with `until: { arrive }`; on arrival `press: [Slot2]` (hoe), `press: [ControllerX]`; next tile; pass 2 swaps seeds and presses `ControllerA`; pass 3 swaps the can and presses `ControllerX`. Every submission re-checks permissions and the goal is still active.
4. `unstuck` (higher priority) fires if `blockedMs` trips twice on the same leg (detour macro); stamina-below mode pauses and defers to the next model turn. On `plotComplete`, the mode deactivates itself, the goal completes, and the next model turn's injected section reads: "field_work done: 15 tilled, 15 planted, 15 watered, 2 stuck-detours." The body never stood idle waiting for a model.

**"Get to the ladder" (monsters + low health).**

1. Model sets the goal, activates `seek_ladder` (low priority) and leaves `danger_flee` / `cornered_fight` at their default-on survival settings. It does not schedule any monster interaction itself.
2. `seek_ladder`'s macro walks toward the ladder with `until: { arrive: ladderTile, monsterWithin: 3 }` and `fastState: true`. A monster closes in: the **adapter** interrupts the walk within one game tick — no model call, no plugin loop iteration even.
3. The selector evaluates predicates on the next poll: `monster within 3 && health < 35%` → `danger_flee` (priority 90, `interrupts: "all"`) wins: path directly away, put ≥ 6 tiles between body and monster; if pathing fails while the monster is adjacent (cornered), `cornered_fight` swings the weapon (`press: [Slot4]`, `press: [ControllerX]` — monsters die to one swing in the sim). At sim speeds (`walkPxPerTick: 4`, `tilePx: 64`, 60 Hz ticks) a monster 3 tiles out arrives in ~0.8 s; an LLM round-trip is seconds — this tier is not optional in the mine.
4. When `stopWhen: { noMonsterWithinTiles: 6 for 1500ms }` clears, the selector falls back to `seek_ladder`; the goal was never ended (pause-holds semantics preserved). The next model turn gets the auto-message pattern from Mindcraft ("Your previous action was interrupted by danger_flight") and can re-plan: drink, retreat to the ladder, or re-arm.

**A mode table entry (data, not code):**

```json
{ "id": "danger_flee", "priority": 90, "interrupts": "all", "requires": "survival",
  "when":     { "monsterWithinTiles": 3, "healthBelowPct": 35 },
  "macro":    "retreat_from_nearest_monster",
  "params":   { "minDistanceTiles": 6, "maySwingIfCornered": true },
  "stopWhen": { "noMonsterWithinTiles": 6, "forMs": 1500 } }
```

`when`/`stopWhen` are predicates over the adapter's declared state vocabulary; `macro` names a procedure in the fixed macro library (walk-with-until, slot+press, path-away); `requires` names the permission class the entry hangs from. The selector engine never mentions Stardew; this JSON does.

## How it fits the DSH seams

- **Seam 6 — body port + helper libraries (the load-bearing seam).** The `ModeSelector` (fixed interpreter, game-agnostic, ~200–400 lines) and the macro library (thin compositions over `navigation.ts`/`walk.ts` that emit `BodyInputStep[]` with `until` + `fastState`) live in the plugin exactly where `navigation.ts` lives today. **No separate process and no side runtime**, and honestly why: the loop is a *stateless function of state* — no model, no planner daemon, no training, no IPC — so an ordinary timer in the existing plugin process suffices; anything more would violate the "no second harness" rule for zero gain. The fastest tier isn't even ours: `until`/`fastState` execute inside the game's own process, which the body protocol (`packages/contracts/src/body.ts`, line ~243: "Ask the adapter for a faster state cadence while this task runs (reflexes)") already shipped for exactly this purpose.
- **Seam 1 — tools.** `modes_inspect` (dump table + active entries + recent mode events) and `modes_set` (enable/disable/re-parametrize entries — a validated declarative diff, cancellable with the caller's turn like every body tool). The model may also keep driving raw `body_input`/`body_walk_to` directly; the reflex tier is a substrate under the model, not a wall around it.
- **Seam 2 — prompt sections.** A per-turn body-status section: active goal binding, active mode, interrupts since the last turn (Mindcraft's auto-message, made a section).
- **Seam 3 — turn-flow hooks.** `agent/pre-step` injects that section and the mode-event digest; goal rounds bind/dissolve directives to DSH goal state.
- **Seam 5 — DSH goals.** The model still creates/updates goals through DSH; the plugin *observes* goal state to gate productive modes (a `field_work`-class mode runs only while its goal is active — this is the anti-unattended-farming latch). `session/cancel` (pause) cancels the active body task and disarms non-survival modes; survival modes degrade to "stop / step away."
- **Seam 7 — local files.** `modes-<game>.json` (the per-game table, player-readable and diffable) and `mode-log.jsonl` (tick, predicate snapshot, winner, action, outcome) under the plugin's bridge directory, next to the memory ledger.
- **Seam 4 — setup callback** loads and validates the table against the adapter's `bodyDeclaration` (unknown input id, legend char, or macro name = load error, surfaced, never a silent fallback).

## Best evidence

- **KRAFTON PUBG Ally (NVIDIA ACE)** — a shipped co-op AI teammate whose architecture is precisely this split: on-device quantized Mistral-NeMo-Minitron-2B SLM for intent/speech, behavior tree at game tick rate for movement/aim/combat reactions, so "reflex-level actions never have to wait for the model"; they moved on-device because cloud round-trips "made responses feel too slow for live squad communication," and state that defining the boundary between the two layers was a core engineering effort. https://developer.nvidia.com/blog/how-krafton-built-pubg-ally-a-co-playable-character-powered-by-nvidia-ace
- **Mindcraft `modes.js`** — the open-source existence proof (~5.9k stars): priority-ordered modes (`self_preservation`, `unstuck`, `cowardice`, `self_defense`, `hunting`, `item_collecting`, `torch_placing`, `elbow_room`, `idle_staring`) with per-mode `interrupts`, run by a fixed controller every tick; modes gate *actions* (not the prompt — `prompter.js` has no modes placeholder), and an interrupted LLM action gets an auto-message. https://raw.githubusercontent.com/mindcraft-bots/mindcraft/develop/src/agent/modes.js
- **DPT-Agent (ACL 2025 main)** — real-time *simultaneous* human-AI collaboration (Overcooked): system 1 is an FSM plus code-as-policy for "fast, intuitive, and controllable decision-making"; system 2 is the LLM with Theory-of-Mind and asynchronous reflection; claims first autonomous success at real-time simultaneous collaboration. https://arxiv.org/abs/2502.11882 (code: https://github.com/sjtu-marl/DPT-Agent)
- **SwiftSage (NeurIPS 2023 spotlight)** — the fast/slow arbitration precedent: a small fast policy handles routine steps, an LLM is invoked only on hard states via a value-function heuristic; outperforms SayCan, ReAct, and Reflexion on ScienceWorld. https://arxiv.org/abs/2305.17390
- **Brooks' subsumption architecture (1986)** — layered priority reactive control where higher layers subsume lower ones and "the world is its own best model"; the ancestor of both mode tables and our adapter-side `until` conditions, with the known weakness (no deliberation) that our system 2 exists to patch. https://en.wikipedia.org/wiki/Subsumption_architecture
- **Talker-Reasoner (2024)** — the general argument for the split at agent level: fast intuitive module + slow deliberative module yields modularity and *decreased latency* by design. https://arxiv.org/abs/2410.08328

## Extensibility across games

The judge weights this above all; the mode-table design is built around it:

- **One engine, N games.** The selector (priority scan, interrupt semantics, permission gating, logging) is fixed code shipped once, tested once, identical for every game. Everything game-specific is **data**: `modes-<game>.json` plus, at most, one or two new macros if the new body needs a motion primitive the library lacks.
- **The table's vocabulary is not invented per game — it is the adapter's declaration.** `bodyDeclarationSchema` already exports the input list with roles (`up/right/down/left/action`), the tile legend, state field descriptions, and limits. Predicates (`monsterWithinTiles`, `healthBelowPct`, `itemInSlot`, `tileInRect`, `blockedForMs`) and macro parameters are assembled from a fixed combinator library parameterized by *that* vocabulary. The setup callback cross-validates table against declaration, so a wrong porting attempt fails at load with a named error instead of misbehaving in play.
- **The LLM can author the port itself — because it writes data, not code.** Hand the model `modes_inspect` + the new game's declaration and it can draft a candidate table; the engine validates it against the closed vocabulary before activation. This is the crucial difference from LLM-authored behavior trees or skill libraries: the model produces a small declarative artifact with bounded expressive power (predicates, priorities, macro refs), executed by a fixed interpreter — no generated control flow, no runtime code, no sandbox question. LLM-as-author is safe exactly where LLM-as-executor is not.
- **Porting cost is measurable, and we volunteer to measure it.** The bench's `toy2` (different state/input vocabulary) ports as: same engine, one new JSON table, possibly one macro. Compare: hand-written BTs (per-game code), LLM-BT (per-session re-generation plus an execution engine anyway), skill libraries (per-game code generation with a trust surface), GOAP/HTN (per-game domain authoring, per-game plan validation), model-level agents (per-genre model). Every rival pays engine *or* generation cost per game; we pay data.
- **Honest cost:** the *first* game pays for the predicate combinator library and the discipline of macro design. That is a one-time engine cost, amortized exactly like `navigation.ts`'s A* was.

## Latency, trust, and debuggability

- **Latency (our strongest suit).** Three tiers, worst to best: model turn (seconds) — used for goals and policy only; reflex poll (~100–250 ms) — mode switches and macro submissions; adapter `until` (one game tick) — "a monster came within N tiles" stops the body *inside the game process*. In the mine scenario the body reacts in ~0.8 s to a monster 3 tiles out without a single token spent; the pure-tool-calling baseline spends a model round-trip per surprise while the body stands idle — visible to a live co-op partner, per the brief. PUBG Ally's team reached the same conclusion for a shipped shooter.
- **Trust and the permission boundary.** The mode table *is* the permission surface: each entry carries `requires: <permission class>`, so "no combat" is deleting/revoking one class, "keep survival only" is one switch, and revocation is re-checked **every selector tick** — it lands within one poll, not at the next model turn, which is the honest answer to "where does the player's revocation land when the reflex layer acts between turns." Productive modes additionally require an active DSH goal created from player words, and complete-and-stop when the goal ends; default-on modes are protective only (flee, unstuck, idle) — the architecture cannot become an unattended farm because nothing productive runs without a live, player-originated goal. Fixed reflexes also cannot improvise: the worst case is bounded by a table the player can read.
- **Debuggability.** The selector is deterministic over logged state, so any incident replays exactly: `mode-log.jsonl` records tick, predicate values, winner, action, outcome — "why did you run?" answers as "danger_flee: Grub within 2 tiles, health 22%," with the task-status `reason` ("monster", "blocked", "arrived") from the adapter corroborating. Misbehavior is either bad data (a table edit — diffable) or an engine bug (one fixed place, unit-testable), never an emergent chain of model improvisations.

## A minimal prototype on the sim

- **Harness:** import `SimAdapter` (unmodified) behind a bench wrapper; add a `ModeSelector` module (fixed engine) plus two table fixtures (`modes-farm.json`, `modes-mine.json`) and a small macro library over `walkTo` + slot/press steps.
- **LLM side (system 2), scripted stub for determinism** (per TASK.md stub rules; a real GLM call if the harness allows): issues the DSH goal and one `modes_set` call per task; receives the mode-event digest between tasks. Record which numbers come from the stub.
- **Farm scenario:** stub binds `field_work` to the plot rect; engine performs till → plant → water over the tiles using `until: { arrive }` legs; `unstuck` handles `blockedMs` detours. Compare against the pure-tool-calling baseline: LLM calls per task, wall-clock, idle ratio, success rate.
- **Mine-like scenario (bench wrapper, not sim edits):** monsters with simple chase logic, low starting health, a ladder tile. Modes: `seek_ladder` (walk with `until: { arrive, monsterWithin: 3 }`, `fastState: true`), `danger_flee`, `cornered_fight` (weapon swing kills in one hit). Measure: deaths avoided vs baseline needing a model turn per encounter, interrupt counts, recovery time to ladder.
- **Porting cost:** copy the engine into `bench/toy2`, author `modes-toy2.json` against toy2's declaration, count changed/added lines vs the engine's size; report table-LOC vs engine-LOC separately.
- **Metrics:** success rate, LLM calls/task, wall-clock, idle ratio, stuck/recovery count, product LOC (engine vs data separated), porting lines.

## Anticipated attacks and your answers

1. **"A mode table is just an anemic behavior tree."** In engine terms it is a BT with exactly two node types (priority selector + interrupt decorator) — deliberately anemic. What we claim is not a richer control-flow language but a different *ownership boundary*: the tree rival ships per-game trees as code/graph plus a runtime; we ship one fixed 200–400-line interpreter for all games and per-game *data* validated against the adapter's closed declaration vocabulary. If a rival wants to say "modes ⊂ BTs," we accept the subset relation and rest the case on the split (LLM policy above, fixed interpreter below) and on load-time validation of data against the declaration — neither of which a BT engine gives you for free.
2. **"The LLM ends up hand-holding modes anyway."** The directive surface is small: one goal binding plus a handful of `modes_set` params, and between turns the loop needs nothing — Mindcraft's modes run every tick autonomously and message the LLM only on interrupt; PUBG Ally's reflexes "never have to wait for the model." Hand-holding appears exactly when the table lacks a predicate or macro the situation needs — which is the correct pressure signal: the durable fix is a validated data edit (which the model itself can propose via `modes_set`/table draft), not a one-off burst of manual `body_input` calls.
3. **"Predicates per game are the real porting cost."** Partly true for game one: we pay once for the combinator library. After that, predicates are compositions over the *declaration's* existing vocabulary (legend, input roles, state fields with descriptions — the contract already mandates them), so each new game authors bindings, not predicate code. The bench's toy2 port will quantify this honestly: if the port costs more than the table, we lose the point on the numbers.
4. **"Reflexes can fight the model's intent — who is responsible when they conflict?"** Priority is declared data, not an emergent property: only survival entries carry `interrupts: "all"`; everything else yields to the model's explicit current action. Every preemption writes a logged event and surfaces in the next turn's body-status section (Mindcraft's auto-message pattern), the model can pin any mode off with one tool call, and each entry hangs from a revocable permission class re-checked per tick. Responsibility is therefore attributable by construction: a named mode entry, with predicate values and outcome, in a replayable log — unlike conflicts inside a learned policy or an LLM's mid-turn reasoning.
5. **"This is scripting — it violates the repo's design principle (guide, don't script)."** We argue it head-on: the operating model demands a stated reason the model or harness cannot do the work, and here it is physics — a monster 3 tiles out in the sim arrives in ~0.8 s (`walkPxPerTick 4 / tilePx 64` at 60 Hz) while model round-trips run seconds, and DSH offers no sub-second seam (tools live inside turns; hooks live at turn boundaries). The repo itself already locates "reflexes" in the plugin (README, Raw Body row) and shipped `until`/`fastState` with "reflexes" in the comment. The principle is preserved where it matters: choice lives with the model — goals, mode selection, thresholds, table edits are all model- and player-authorable policy; the fixed part is an interpreter, no more a behavior tree than `navigation.ts`'s A* is a route.
6. **"Stardew is slow and pauseful; latency doesn't matter."** The companion's world does not pause when the model thinks — it shares unpaused time with a live player, the brief calls idle bodies visible, and the mine scenario (monsters + low health) is precisely the case where a seconds-long gap is lethal. And latency is not only survival: it is the difference between a companion that moves like a co-op partner and one that freezes between thoughts — the exact lesson KRAFTON states for shipping a squadmate.
