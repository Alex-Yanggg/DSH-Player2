# Advocate: pure LLM tool calling (today's baseline)

## Claim

The behavior loop should be owned by exactly what owns it today: the model, deciding turn by turn over a small set of composable tools (`world_observe`, `world_find`, `world_map`, `world_locations`, `body_walk_to`, `body_controls`, `body_input`) plus DSH goals and persona prompt sections. Every rival proposal adds a second artifact between the model and the body port — a tree, a domain file, a modes table, a learned policy — and every such artifact is per-game fixed logic that must be re-authored, re-tuned, or re-trained for each new game, which is precisely the axis the judge weights most. Pure tool calling has **zero per-game behavior code**: the only per-game surface in the entire stack is the adapter's declaration (button descriptions in plain words, a tile legend, state fields, limits, warps), which is data, not logic. The repo's own design principle is unambiguous: "Player2 runs on a harness... The companion thinks for itself; the product gives it perception, hands, and thinking guidance, not a fixed behavior tree" and "Fixed logic needs a stated reason why the model or the harness cannot do it" (`docs/operating-model.md`). I am the only advocate who does not need that excuse. And the reactive substrate rivals claim requires their layer — tick-rate danger interrupts, blocked-tile replanning, unattended locomotion — already exists in this architecture, split correctly between the adapter (`until` conditions, `fastState`), a helper library the model composes (`walkTo`), and the model itself (decisions). The industry reached the same conclusion: ReAct's interleaved reason-act loop beats acting-only and reasoning-only baselines on embodied tasks ([Yao et al., ICLR 2023](https://arxiv.org/abs/2210.03629)), Anthropic tells agent builders to use "the simplest solution possible" and treat tool interfaces as first-class products ([Anthropic, Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents)), and the tool-declaration pattern is now an open standard with a cross-vendor ecosystem ([MCP](https://modelcontextprotocol.io/introduction)).

## Mechanism

The loop for **"plant and water the parsnips"**, as the code runs today (`packages/dsh-companion-plugin/src/body/tools.ts`):

1. **Goal intake.** The player's words become a DSH goal (DSH owns goal state, queueing, cancellation — seam 5). Goal rounds drive the model's turns; a paused game holds the goal.
2. **Perceive.** The model calls `world_observe`, which renders raw state as compact text: clock, "You: Farm (12,8) facing down, stamina 240... Toolbar: 1: Hoe; 2: Watering Can (water 40/40); 3: Parsnip Seeds x15", nearest objects nearest-first with per-kind facts (`dry`/`watered`, crop phase, `READY`), characters with hp, exits. Then `world_find kind=dirt` enumerates the plot tiles; `world_map` shows the raw grid with the legend if geometry is unclear.
3. **Decide and compose.** The model writes the plan itself: for each tile — `body_walk_to {x, y, mode: "adjacent"}` (stop next to it, face it), then `body_input` with `press: ["Slot1"]` + `ControllerX` (hoe), re-select the can, `ControllerX` (water), `Slot3` + `ControllerA` (plant). Nothing in the adapter knows "till" or "water"; the model composes these from `body_controls`' declared plain-word descriptions and reads the honest result text back: "Events: used: Hoe at 12,8. Your toolbar changed: Parsnip Seeds -1. Stamina 236." Verification is built into every result (`describeRun` diffs inventories; `world_find readyOnly` confirms watered tiles).
4. **Locomotion without the model.** Inside `body_walk_to`, `walkTo` (`walk.ts`) does: snapshot state → A* over the exported grid (`navigation.ts findPath`, 40k-node cap) → collapse straight runs into single timed holds (`pathToSteps`, durations computed from the *declared* `tilePx`/`walkPxPerTick`/`tickMs`) → play up to 64 steps as one raw-input task with `until: { blockedMs: 600 }` → look again → re-plan, ≤14 legs. **If a step blocks, `settle()` marks the next tile on the path and the next leg routes around it**; if no path exists it gives up honestly and names the obstruction ("in the way: Stump at (10,4)") rather than looping. Cross-location hops BFS the exported warp graph and handle walk-warps vs. door-warps (walk adjacent, face, press action). During a leg the model is not in the loop at all — the body walks for seconds on held buttons.
5. **Close and report.** The model checks the plot via `world_find`, speaks as a person (never tile coordinates), updates the goal.

The loop for **"get to the ladder"** (monsters, low health):

1. `world_observe` lists monsters with hp and positions; `world_map` shows the two corridors.
2. **The model makes the risk decision** — the exact judgment a fixed layer cannot make without game-specific tuning: sprint the short corridor, take the long safe one, or clear the monster first (select weapon slot, one-tick face tap, `ControllerX`; in the sim monsters die to a swing).
3. **Arming the reflex is a tool argument.** For the dangerous stretch the model submits `body_input` steps with `until: { monsterWithin: 4 }`. From then on the **adapter** ends the task the tick a monster closes inside 4 tiles — in `sim-adapter.ts` this check runs inside `playTick`, once per sim tick, entirely independent of model latency — and returns `interrupted (monster)` with fresh state. The task frame also carries a `fastState` flag whose contract comment is literally "ask the adapter for a faster state cadence while this task runs (reflexes)" (`packages/contracts/src/body.ts`). This is a system-1 interrupt the *model* configures and the *adapter* executes at tick rate.
4. On interrupt, the model re-decides with one round trip: fight, retreat, or reroute — a new `walkTo` leg, which replans around the monster's tile automatically because `Walkability` blocks non-farmer characters.
5. Ladder reached via `body_walk_to` or an action-warp leg; the goal round ends.

Division of labor, precisely: **adapter** = tick-rate evaluation of `until` (arrive/blocked/monster/warped) and raw state cadence; **helper library** = deterministic geometry (A*, step timing, leg replanning, honest failure strings); **model** = every decision, composed from tool results. That is the whole behavior architecture.

## How it fits the DSH seams

Trivially — because this architecture **is** the seams, nothing else:

- **Seam 1 (tools):** `createBodyTools` in `tools.ts` is seven `defineTool` calls, each executing under the caller's turn cancellation (`exec.signal`) — "a cancelled turn stops the body too."
- **Seam 2 (prompt sections):** persona, policies ("act on a request at once by creating a goal", "never internal terms or tile coordinates"), knob tendencies — thinking guidance, not branch logic.
- **Seam 3 (`agent/pre-step`):** turn markers route `[chat]`/`[day-start]`/`[day-end]`/`[resume]`; no behavior code.
- **Seam 5 (DSH goals):** DSH owns goal lifecycle; the plugin only feeds and observes.
- **Seam 6 (body port + helper libraries):** the port is raw state/raw input; `navigation.ts`/`walk.ts` are exactly the seam's sanctioned "whatever helper libraries the plugin ships" — a library the model *chooses* through `body_walk_to`, not a semantic adapter command (zero Stardew words in it; it runs unchanged on the sim).
- **Seam 7 (local files):** the memory ledger.

**No side runtime.** No planner daemon, no interpreter for tree data, no skill-code executor, no model server, no training loop. The "behavior layer" is: the model + 7 tools + prompt lines. Rivals must either live inside these seams (shrinking into what I already have) or explain their second runtime — the brief says that framing decides in/out of bounds.

## Best evidence

- **ReAct** — interleaving reasoning traces with environment actions beat acting-only and reasoning-only baselines on embodied/interactive tasks: +34% absolute success on ALFWorld and +10% on WebShop with 1–2 in-context examples; trajectories are human-readable. https://arxiv.org/abs/2210.03629
- **Anthropic, "Building effective agents"** — the strongest practitioner authority: find "the simplest solution possible, and only increase complexity when needed"; agents are systems where LLMs "dynamically direct their own processes and tool usage"; invest in the agent–computer interface (tool descriptions) as much as the HCI. This whole repo's tool layer is exactly that investment. https://www.anthropic.com/engineering/building-effective-agents
- **Model Context Protocol** — tool/resource declaration behind one open standard, supported by Claude, ChatGPT, VS Code, Cursor and more; the "declare capabilities, model composes" pattern is the industry's interchange format for agent capabilities — which is what our `BodyDeclaration` is. https://modelcontextprotocol.io/introduction
- **Survey on LLM-based game agents (ACM CSUR 2026)** — the field's reference architecture for LLM game agents is "memory, reasoning, and perception-action interfaces": exactly tools + prompt + ledger, no intermediate behavior formalism. https://arxiv.org/abs/2404.02039
- **BALROG + NVIDIA NIM run** — honest frontier numbers: DeepSeek-R1 averaged 34.9% across six game environments (beating Claude 3.5 Sonnet's 32.6%), confirming both that game agents are hard and that all architectures inherit model-rate competence — gains come from the model, not from a behavior layer. https://developer.nvidia.com/blog/benchmarking-agentic-llm-and-vlm-reasoning-for-gaming-with-nvidia-nim/
- **ClickHouse LLM latency guide** — the honest cost side, with numbers I use below. https://clickhouse.com/resources/engineering/llm-inference-latency

## Extensibility across games

This is the judge's weighted criterion, and it is where the gap is decisive. Enumerate the per-game surface of each candidate: a behavior tree needs nodes per mechanic; a modes/reflex layer needs a table per game; a GOAP/HTN domain needs actions, effects, and preconditions per mechanic; a learned policy needs training data per game; an LLM-written skill library needs a verification harness per game. Pure tool calling needs exactly **one artifact: the `BodyDeclaration`** — `inputs` (≤48 buttons, each with a plain-word `description` "a model can read", optional `role` up/right/down/left/action, cheat flag), `state.fields`, the tile `legend`, `limits` (tick, walk speed, tile size), and the raw state stream (objects with per-kind `extra`, characters, warps, menus). That is data the adapter *declares*, not behavior code the plugin *contains* — "the adapter never learns 'walk to' or 'chop the tree'" (`packages/contracts/src/body.ts`).

The proof is already in the repo: `sim-adapter.ts` is a *completely different world* (toy tiles, hoe/can/weapon semantics, shops, monsters) behind the *same* `BodyPort`, and the plugin, all seven tools, the navigation library, and the prompts run on it **unchanged**. The bench's `toy2` porting test (a grid crafting game with keys instead of tiles/tools) is precisely my home ground: porting cost = write one adapter that declares its vocabulary; for me that is the whole cost, for the rivals it is that *plus* re-authoring their behavior layer. Stardew is the first game, not the product; a declaration is authorable by an adapter writer in any game with a controller; MCP's ecosystem shows declarations-as-capability scale across thousands of integrations with zero per-integration agent code. Unbeatable on this axis: my per-game fixed-logic count is zero and cannot go lower.

## Latency, trust, and debuggability

Honest numbers first. End-to-end LLM latency ≈ TTFT + (output tokens − 1) × TPOT; well-tuned deployments see TTFT of ~200–500 ms (multi-second on long contexts) and 10–50 ms per output token (20–100 tok/s); a 300 ms TTFT + 30 ms/token turn with 500 output tokens takes **over 15 seconds**, and reasoning models can emit ~2k thinking tokens first ([ClickHouse](https://clickhouse.com/resources/engineering/llm-inference-latency); measurement methodology: median TTFT/output speed at ~10k-token prompts, [Artificial Analysis](https://artificialanalysis.ai/methodology/performance-benchmarking)). So yes: at a genuine decision point, the body can stand for seconds-to-tens-of-seconds. That is my weakest flank; here is why it is narrower than it looks, using mechanisms already in the seams:

- **The body is not idle during most of the task.** `walkTo` legs run unattended: straight runs collapse into single holds timed from declared limits, so one model round trip buys many seconds of walking; the hoe/plant/water batches are multi-step `body_input` tasks that execute to completion or interrupt. Idle time concentrates at decision points, which is where a co-op partner hesitating reads as *thinking*, not broken.
- **Danger does not wait for the model.** `until.monsterWithin` is evaluated by the adapter per tick; `blockedMs` stops windmilling at 600 ms; `fastState` requests faster state cadence. The reactive guarantee is tick-rate, not model-rate.
- **Turn size is engineered small.** `renderObservation` caps at 45 nearby objects; `renderMap` windows to radius ≤ 20; tool outputs are terse text — TTFT stays in the short-prompt regime.
- **Trust and debuggability are the strongest in the field.** One causal chain — the model's reasoning trace plus tool I/O — is the complete explanation of any behavior, and DSH's session logs are the single record ("The mod keeps no logs of its own; DSH's session logs are the record", `docs/architecture.md`). Every tool returns honest facts (`NOT REACHED: no walkable path...; in the way: Stump at (10,4)`), events, stamina and inventory diffs. Multi-layer rivals must correlate model logs with tree state / planner traces / policy decisions — and a Berkeley study of 1,600+ failure traces finds the majority of agent-system failures come from *system design and inter-agent misalignment* categories, not raw model capability ([MAST](https://arxiv.org/abs/2503.13657)): fewer layers, fewer failure classes to debug.
- **Determinism:** none at the model layer, by design — the repo's own principle. The deterministic substrate (A*, `pathToSteps`, `settle`) is pure and unit-tested without a model; acceptance for model-level behavior is statistical (fixed seeds, ≥10 runs — exactly the bench's protocol), as it is for any model product. A BT's determinism is worthless if its semantics must be rewritten per game.

## A minimal prototype on the sim

- Mount `createBodyTools` over `SimAdapter` exactly as the plugin does today (same seven tools, same `walkTo`), driven from a bench script with per-seed scenario setup.
- Scenarios: **farm** — till/plant/water N parsnip tiles on the toy plot; **mine-like** — reach a ladder tile with hostile monsters and low starting health (a bench wrapper, not adapter edits).
- Model: a scripted "model stub" issuing the documented tool sequence by default, plus a real GLM call path if a key is available; stub-sourced numbers marked as such.
- Metrics per the bench: success rate, tool calls per task, wall-clock, idle ratio (no active body task while awaiting the model), stuck/recovery count (blocked legs, `monster` interrupts, re-plans), and product LOC — which should be ~0 new lines beyond scenario setup, because the prototype *is* the shipped code.
- Porting arm: point the same harness at `bench/toy2`'s adapter; count changed lines — expected: one new declaration, zero plugin changes.

## Anticipated attacks and your answers

1. **"Idle while thinking is visible to the co-op player."** True at decision points; quantified above (worst case >15 s on a 500-token turn). But the visible cadence of the task is not the model's cadence: legs and input batches run unattended, and the interrupt system is tick-rate. The honest comparison is against rivals' *first* decision too — every architecture except a pure reflex table pays the same first-round-trip before the body moves; and a reflex table that moves instantly moves *wrong* in novel situations. Mitigation levers already in the seams: longer verifiable primitives (`body_walk_to` mode), batched `body_input` with `until`, compact tool outputs, and `[resume]`-style re-arming after pause.
2. **"Long-horizon dithering and replanning loops."** Admitted and measured: best GPT-4 agents scored 14.41% vs human 78.24% on realistic long-horizon tasks ([WebArena](https://arxiv.org/abs/2307.13854)), and frontier models average ~35% on game suites ([BALROG/NVIDIA](https://developer.nvidia.com/blog/benchmarking-agentic-llm-and-vlm-reasoning-for-gaming-with-nvidia-nim/)), with diagnosed gaps in planning and spatial reasoning ([SmartPlay](https://arxiv.org/abs/2310.01557)). Three answers: (a) our goals are delegated, bounded, and *verified in every tool result* (inventory diffs, `watered`/`READY` flags, arrive/blocked reasons) — dithering is detected, not just suffered; (b) the loop structurally cannot spin: `walkTo` caps at 14 legs and reports failure honestly, terminal statuses are finite, DSH bounds goal rounds and the player can pause/cancel at any time; (c) when stuck, the right behavior is to *ask the player* — a persona trait here, and one no autonomous planner layer has.
3. **"No determinism."** The substrate (A*, step timing, `settle`) is deterministic and tested without a model; model-level behavior is accepted statistically over fixed seeds — the same standard any rival with an LLM anywhere in its loop must meet (which is all of them). Determinism that survives only until the next game port buys nothing on the judge's criterion.
4. **"Monsters will eat it while it thinks."** The monster interrupt is armed *before* the danger and evaluated by the adapter each tick (`sim-adapter.ts playTick`), so monster reaction time is tick-rate regardless of model latency; on interrupt the model gets `interrupted (monster)` + fresh state and decides fight/flee/reroute. And choosing *which* corridor is safe at 30 hp is exactly the kind of novel, game-specific judgment that fixed layers cannot carry across games without per-game tuning.
5. **"`walkTo` is a semantic adapter in disguise — you have behavior code."** It contains zero game vocabulary: it is geometry over declared data (grid rows, legend, warp graph, `role` buttons, `limits`) — seam 6's sanctioned helper library, and it runs unchanged on the sim. Rival layers hard-code *decisions*; `walkTo` only executes a *decision the model already made* (a target tile) and reports honestly. Fixed logic here has its stated reason, per the design principle: the model cannot press buttons faster than the tick rate.
6. **"Compiling your loop into a tree/skills/modes would be cheaper at runtime."** Cheaper per step, perhaps — and costlier per *game*: each compilation target is a new artifact to author, verify, and port, and a second failure domain ([MAST](https://arxiv.org/abs/2503.13657)). The bench's porting-cost arm is the falsifier: if porting mine to `toy2` costs more than a declaration, I lose the argument on evidence, not taste.
