# Advocate: Utility AI (the Infinite Axis pattern under the LLM)

## Claim

The loop that turns "plant and water the parsnips" into button presses should be owned by a **fixed, tick-local utility evaluator** living in the plugin next to `navigation.ts`: every N ticks it reads the raw state the adapter already exports, scores a candidate-action set where each candidate is scored by multiplying **considerations** — normalized response curves over raw state fields — and executes the argmax (with a commitment bonus so it doesn't dither). The **LLM stays the mind and stays above this layer**: it translates the player's goal into a small, inspectable **policy document** of weights, biases, and added considerations — data, not code — through a validating DSH tool, and it owns talk, judgment calls, and asking the player. This is the only candidate that is simultaneously (a) fast enough for a live co-op world (no model round-trip per micro-action), (b) explainable from logs by construction (every decision is a dump of numbers), (c) honest about the repo's own design principle — it turns "policies and tendencies" from prose into arithmetic the model itself authors — and (d) extensible across games the way the judge cares about: **the evaluator is game-agnostic code; every game-specific thing is a JSON data pack over the adapter's already-declared state fields, legend, and input list.** Utility AI has shipped at the largest scales this field knows — The Sims' needs/advertised-satisfaction core loop and Dragon Age: Inquisition's Behavior Decision System are documented, citable precedents — and 2022-2025 research (SayCan, Eureka) shows exactly the LLM-above / scorer-below split I propose works and that LLMs can author the numeric layer better than humans when given feedback.

## Mechanism

The loop, concretely (for both scenarios the bench uses):

1. **Goal intake (LLM, cold path).** The player's words become a DSH goal (seam 5), as today. On the goal-round `agent/pre-step` marker, the plugin injects a prompt section asking the model to emit (or reuse) a **policy document** through the `behavior_policy` tool (seam 1): goal id, permission scope (which tiles/locations/items), per-action **weights** (plain multipliers), optional **biases** (additive), optional **new considerations** as data, and a deadline/stop condition. The tool validates every referenced field name against the adapter's `declaration()` (`state.fields`, `legend`, `inputs`) — an unknown field is rejected, so a policy can't reference state the adapter doesn't export.
2. **Candidate generation (fixed, hot path).** Each tick batch (every N ticks; the body task schema already has a `fastState` flag "for reflexes", `packages/contracts/src/body.ts`), the scorer pulls `body.state()` and expands a handful of **universal action families** over declared state:
   - `walk-to(location,tile)` — via the existing A* helper, for any tile/warp/ladder the adapter exports;
   - `face-and-use(tile, toolSlot)` — select a toolbar slot (`Slot*` press), face the tile, press the use button (`ControllerX` in the sim);
   - `press-action-on(tile)` — face and press the action button (`ControllerA`);
   - `swing-at(character)` — face the nearest monster tile and press use with a weapon held;
   - `flee-to(safeTile|warp)`;
   - `wait/report-done` (a null action that always scores low but nonzero).
   Candidates are **generated, not enumerated by hand**: every dirt tile in scope spawns till/plant/water candidates; every monster in range spawns a swing candidate; the ladder tile spawns a walk candidate.
3. **Scoring (fixed arithmetic).** Each candidate's score = product of its considerations × the LLM's weight for that action family (+ bias). Considerations are response curves over raw inputs derived only from exported state: distance in tiles, stamina fraction, health fraction, monster proximity in tiles, per-object `extra` flags (`watered`, `crop`, `passable`), inventory contents. Preconditions are 0/1 curves — a zero kills the candidate outright (standard IAUS practice: consideration scores are multiplied, so any zero vetoes the action — per the IAUS manual and the ShaggyDev walkthrough).
4. **Execution.** Argmax (or a random pick within a small threshold of the top, Sims-style, so it doesn't look robotic) gets a **commitment bonus** (hysteresis) and is executed as a replaceable, cancellable input task with `until` conditions — exactly the body task the port already accepts. A task that ends `interrupted` (monster, blocked) just becomes state; the next scoring tick re-decides.
5. **"Plant and water the parsnips."** The LLM's policy says: scope = the delegated plot's tiles; weights `{till: 0.9, plant: 1.0, water: 1.0, walk: 1.0, flee: 1.0}`; stop = "every in-scope dirt tile has a crop and is watered". No sequence is written anywhere. On a fresh tile: `plant(tile)` and `water(tile)` score 0 (precondition: tilled), so `till(tile)` wins; the moment the till event lands, `till`'s precondition flips to 0 (already tilled) and `plant` wins; then `water`. **Sequencing emerges from state preconditions under the same scorer** — the same trick The Sims uses to make Sims eat-then-shower-then-sleep with no script (GMTK's deep-dive documents exactly this: advertised satisfactions weighted by current motives, personality weights, proximity, and randomness among top scorers).
6. **"Get to the ladder" (monsters + low health).** Same scorer, different policy: weight `walk-to(ladder)` high, but the survival considerations are universal. `flee-to(warp)` carries a steep logistic over `healthFraction` — near 0 at full health, spiking to ~1 below ~30%. `swing-at(monster)` carries an inverse curve over `nearestMonsterTiles` and the persona's **risk knob** as a weight. At full health the ladder walk outscores everything; a monster closes inside 2 tiles → the swing's proximity curve peaks and interrupts; health drops under the logistic midpoint → flee dominates with no branch anywhere that says "if health low then flee". This is the emergent-priorities property BTs fake with branch order and utility systems get for free (the Wikipedia utility-system overview states it directly: behaviors "sort themselves by score" instead of designers placing them in a priority tree).

One example consideration, as the policy data actually looks (this is what the LLM authors and what the scorer evaluates):

```json
{
  "action": "flee-to-warp",
  "weight": { "source": "goal:get-to-the-ladder", "value": 0.8 },
  "considerations": [
    { "input": "healthFraction",
      "curve": { "kind": "logistic", "midpoint": 0.30, "steepness": 12 },
      "note": "near 0 when healthy, ~1 below 30% health" },
    { "input": "nearestMonsterTiles",
      "curve": { "kind": "inverseLinear", "max": 12 } },
    { "input": "warpWithinTiles",
      "curve": { "kind": "quadraticDecay", "max": 15 } }
  ]
}
```

Evaluation per tick is `score = Π curve(input) × weight + bias` — dozens of floats over at most a few hundred candidates, microseconds; the "AI at Massive Scale" GDC talk this pattern comes from was explicitly about running it for MMO-scale agent populations.

## How it fits the DSH seams

All seven, nothing new, **no side process, no second runtime, no model in the hot loop**:

1. **Tools (seam 1):** one new `defineTool` — `behavior_policy` — that writes/updates the active goal's policy document (weights, biases, considerations as JSON) after validating field references against the adapter declaration; plus `behavior_explain`, which returns the last decision's score dump for the model (and the "why are you doing that?" chat path). The scorer itself calls the BodyPort directly, like `walk.ts` does — it does not go through tools.
2. **System-prompt sections (seam 2):** guidance on when to write a policy vs. handle something by hand; the persona knobs (risk, obedience) surfaced as named weights the model may set within bounds.
3. **Turn-flow hooks (seam 3):** `agent/pre-step` on a goal-round marker loads/refreshes the policy for the now-active DSH goal; `[day-end]` may fold learned weight nudges into tomorrow's policy; `[resume]` re-arms the scorer with the paused goal's existing policy.
4. **Setup callback (seam 4):** starts the in-process scoring loop bound to the BodyPort. It is a timer in the plugin's own process, same class of thing as the existing navigation helper — **not** a daemon, not a planner service.
5. **DSH goals (seam 5):** DSH keeps owning goal state, queueing, cancellation, pause. The scorer advances **only** the currently active goal, within the policy's permission scope; when DSH pauses/cancels (player paused the game), the scorer idles — pause holds, and the scorer can never create goals or outlive its goal.
6. **Body port + helper libraries (seam 6):** the evaluator (`utility.ts`, a few hundred game-agnostic lines) sits beside `navigation.ts`/`walk.ts` and uses both the raw port (state, input tasks with `until`, `fastState`) and the walk helper for legs.
7. **Local files (seam 7):** one policy JSON per goal plus append-only score dumps under `<bridge>/behavior/`, exactly the pattern the memory ledger uses. Policies are diffable, versioned, deletable; deleting the goal deletes the policy.

Honest boundaries: the evaluator and the action families are **fixed code** (I defend this below against the design principle); per-game content is data. Nothing here needs a training loop, a model server, or any process outside the plugin.

## Extensibility across games

The judge's top criterion, head-on. Split everything into **universal code** and **per-game data**:

- **Universal (write once, ship in the plugin):** the evaluator (~argmax, curve library: logistic/inverse/quadratic/step, commitment bonus, threshold-random pick); the action families — `walk-to`, `face-and-use`, `press-action-on`, `swing-at`, `flee-to`, `wait` — which are defined over the *body declaration's own vocabulary* (`inputs` with roles `up/right/down/left/action`, hold vs press, slot buttons; `state.fields`; the legend; `warps`). The body contract was explicitly built so "navigation, goals, tactics and choices live on the DSH plugin side" (`packages/contracts/src/body.ts` header) — the utility layer is the missing "choices" half of that sentence, written once.
- **Per-game (a JSON data pack, authorable by the LLM or a human):** candidate generators keyed on object kinds and legend characters ("`dirt` tiles spawn till/plant/water candidates"; "`monster` characters spawn swing candidates"), considerations referencing the new game's declared field names, default curves, tool-to-button mapping read off the declaration's input descriptions. Porting to a second game = new adapter declaration + new pack + **zero evaluator changes**. For the bench's `toy2` (grid crafting game, keys instead of tiles/tools), the pack maps `press-action-on` to a key press and redefines candidates over that game's objects — the porting-cost metric should be mostly JSON lines.
- **New mechanics mid-game:** the LLM adds a consideration ("parallax fishing minigame: score `wait-for-bar-overlap` from `extra.barOverlap`") as data through the validating tool; it never touches code. This is the Sims' content-scalability property (thousands of objects added as advertising data) transplanted to our plugin, and Eureka is the evidence the LLM can do the authoring.
- **Contrast with the rivals on this axis:** a BT — hand-written or LLM-authored-as-data — encodes *structure and order* per game; every new game re-authors the tree and every new behavior must be placed in the tree by hand (Wikipedia's utility-system comparison makes exactly this point: with utility, a new behavior only declares *why it would be useful*, and the sort does the rest). Skill-code libraries (Voyager-style) accumulate per-game code that must be executed, sandboxed, and reviewed. Planners need per-game domain models. Model-level game players need the game's pixels. Utility's per-game surface is the smallest: curves over fields the adapter already promised to export.

## Latency, trust, and debuggability

- **Latency:** the hot loop is floats-over-state — no model call per action, ever. The LLM is consulted once per goal (policy authoring) and on exceptions (stuck, done, permission question), so the body never stands idle waiting on a round trip while executing a delegated goal; the adapter's `fastState` flag gives the scorer higher state cadence during reflex windows. Idle ratio on the bench should approach the pure-BT floor, not the LLM baseline's.
- **Trust / permission boundary:** the policy document *is* the permission card: scope tiles/locations/items, allowed action families, stop condition, weight bounds. The validating tool rejects out-of-scope references; the scorer refuses candidates outside scope; cheat-class inputs are already refused by the adapter. A revoked goal deletes its policy and the scorer idles (pause holds). The companion advances delegated plans only through this inspectable, revocable document — stronger than the baseline, where the permission surface is the whole prompt.
- **Debuggability:** every decision appends a **score dump** — all candidates, every consideration's input value, curve output, weight, product, and the winner — to `<bridge>/behavior/`. A misbehaving companion is explained by reading one line of arithmetic, not by replaying model transcripts. `behavior_explain` surfaces the same dump to the model and the "why did you do that" chat. Weight changes go through a tool call, so they appear in DSH's session logs with full text and diffs. Determinism: same state + same policy ⇒ same scores (modulo the declared randomness window, which is itself a logged parameter).

## A minimal prototype on the sim

Against `packages/dsh-companion-plugin/src/body/sim-adapter.ts` (imported, not modified), in `bench/`:

- **Evaluator module (~200-300 lines):** curve library (step, inverse-linear, logistic, quadratic-decay), candidate = action family × target, product scoring, commitment bonus, top-threshold random tie-break; appends a score dump per decision.
- **Two action-family bindings over the sim's declared inputs:** `face-and-use` = `press SlotN` + face + `ControllerX`; `press-action-on` = face + `ControllerA`; `walk-to` reuses the plugin's A* helper against the sim's grid.
- **Farm scenario (fixed seeds, ≥10 runs):** 3×3 plot of `.` tiles, hoe/watering can/Parsnip Seeds in the toolbar. Candidates: till/plant/water per tile + `walk-to` per candidate tile. Fixed policy (one hand-written JSON standing in for the LLM's — mark it as a stub in results). Success = all 9 tiles `crop` + `watered`; measure steps, wall-clock, stuck count, and lines of code. Then one run variant where the "policy authoring" is a real model call to compare.
- **Mine scenario (wrapper adds monsters + ladder tile + health drain, per TASK.md):** candidates: `walk-to(ladder)`, `swing-at(m)` per monster, `flee-to(warp)`; logistic health consideration on flee. Success = body reaches the ladder alive in ≥X of runs; sweep the health midpoint once to show the tuning knob is one number in data, not code.
- **Porting check (`toy2/`):** rebind candidates to the key-crafting vocabulary; count changed/added lines (target: JSON-only, plus at most a few generator lines) — this is the number the judge should stare at.

## Anticipated attacks and your answers

1. **"Utility tuning is unmaintainable folklore — curve params are magic numbers nobody can reason about."** Folklore is what you get when numbers hide in code. Here every number lives in a per-goal JSON file with provenance (who wrote it, which goal, when), every decision logs the arithmetic that consumed it, and the personas' knobs are named parameters with bounds. The Sims tuned this way for decades across thousands of content items — that's not folklore, that's a shipped content pipeline. And Eureka is direct evidence that LLM-plus-feedback can iterate numeric objectives to **beat expert humans on 83% of 29 tasks**; my score dumps are precisely the feedback surface.
2. **"Enumerating the candidate action set is the real hard part — utility just picks among them."** Partially conceded, and I own it: candidate generation is per-game knowledge. But (a) generators are tiny — "for each object of kind K in scope, spawn the applicable action families" — over state the adapter already exports with descriptions and a legend, so they can be expressed as data too (kind → families); (b) the action *families* are universal because the body contract fixed the input vocabulary (directions, action button, slots); (c) the set can start small and grow by adding considerations/data, never by touching the evaluator. Compare: a BT must enumerate candidates *and* order them *and* write per-branch logic; utility only enumerates and describes.
3. **"No notion of a multi-step plan — parsnips need till→plant→water sequencing, and 'reach the ladder' may need detours."** Sequencing comes from **precondition gates**: 0/1 considerations zero out inapplicable actions, so the argmax walks the correct order per tile with no plan anywhere — the same state-driven emergence that makes Sims eat when hungry without a schedule. Dithering is handled by the commitment bonus (hysteresis) and phase buckets when the policy wants coarse ordering (ShaggyDev documents bucketing as shipped practice, e.g. Zoo Tycoon 2's overriding "dying" bucket). For genuinely long-horizon structure (across locations, across days), the LLM above composes it the SayCan way — re-weighting and re-scoping per phase — while the scorer keeps the body safe at frame rate.
4. **"LLM setting weights is uninspectable — you've moved the black box from actions to parameters."** The opposite: free-form model actions (today's baseline, or Voyager-style generated code) are unbounded text; a policy document is a small typed schema, validated against declared fields, bounded by the permission scope, diffable per goal, logged in the DSH session when written, and revocable with the goal. When behavior surprises, the score dump shows exactly which consideration produced it — try doing that with a 40k-token transcript or a generated Python file.
5. **"This violates the repo's design principle — 'guide, don't script' — it's a fixed decision loop."** Argued head-on: the principle says fixed logic needs a stated reason the model or harness cannot do the job. The reasons are latency and explainability, and they are structural: a live co-op body cannot wait on model round-trips per micro-decision (the LLM game-agent survey names frame-level responsiveness as the binding constraint in real-time games), and DSH's turn logs cannot explain a reflex after the fact. The repo already accepts exactly this trade for A* in `navigation.ts` — fixed code for the same two reasons. Everything the principle actually protects — *what* the companion does, in what mood, how cautiously — lives in data the model authors (weights = tendencies, literally; considerations = policies, literally). I am not scripting behavior; I am making the prose executable and auditable. Where the model can do it end-to-end without violating latency (talking, planning phases, asking the player), it still does.
6. **"Why not Merrill's hybrid — utility inside behavior-tree selectors?"** (If the BT advocate raises it.) Because the judge's criterion is extensibility: Merrill's pattern keeps the per-game *structure* (the tree) as authored code/data and gains only local scoring. My split removes per-game structure entirely — no tree to re-author per game, only curves over declared fields — which strictly dominates on porting cost while keeping the same math.
