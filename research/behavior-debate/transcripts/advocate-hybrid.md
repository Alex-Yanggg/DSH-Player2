# Advocate: a declaration-driven dual-process hybrid (system 2 owns goals and authoring, a validated data-driven executor owns the gaps, a skill library accumulates per-game competence, DSH goals gate everything)

Written 2026-10-24 on `behavior-research`. Approach 8 of the debate (hybrid, self-designed).

## Claim

The behavior loop should be owned by **four components with one shared vocabulary**: (1) the model — system 2 — owns goals, decomposition, *authoring*, and exception handling, on DSH's own turn cadence; (2) a **fixed, game-agnostic executor** — system 1 — owns continuous control between model turns at poll cadence, but executes only **directives**: small declarative artifacts (priority-ordered behaviors binding state predicates to macro parameters) whose entire vocabulary is the adapter's existing `bodyDeclaration` — the same declaration the model's tools render; (3) a **skill library** on disk (seam 7) that stores validated, human-inspectable directive bundles and, exceptionally, reviewed code skills — CoALA's "procedural memory"; (4) **DSH goals** as the sole permission gate: nothing productive executes unless bound to a live, player-originated goal. Composition beats any single layer because the failure modes of the rivals are complementary and each is fixed by a layer the rival refuses to include: pure tool calling dies on latency (the body stands idle through every surprise), fixed trees/mode tables die on novelty (nothing in the table knows what "parsnips" are), skill libraries die on trust (LLM-written code on the host) and on latency between calls, planners die on per-game domain authoring. The field's own evidence is composition-shaped: KRAFTON's shipped PUBG Ally is explicitly an SLM decision core over a behavior tree at game tick rate, and reports that "a significant amount of engineering effort went into defining the boundary between those two layers" and that "reflex-level actions never have to wait for the model" ([NVIDIA developer blog](https://developer.nvidia.com/blog/how-krafton-built-pubg-ally-a-co-playable-character-powered-by-nvidia-ace)); DPT-Agent (ACL 2025 main) reports empirically that "System 1 or System 2 alone is insufficient" for real-time simultaneous human-AI collaboration ([arXiv:2502.11882](https://arxiv.org/abs/2502.11882)); SwiftSage's fast/slow arbitration beats ReAct, SayCan and Reflexion ([arXiv:2305.17390](https://arxiv.org/abs/2305.17390)); Voyager shows an LLM-authored, validated, inspectable skill library is what compounds per-game competence and even transfers to a new world ([arXiv:2305.16291](https://arxiv.org/abs/2305.16291)). No shipped or published system I found is monolithic; the hybrids win exactly when each layer's ownership is named — which is this proposal's actual content.

## Mechanism

One loop, four ownership tiers, one vocabulary. **Downward**: player words → DSH goal → model turn → a *skill binding* (library skill id + parameters + goal id) → executor. **Upward**: task statuses, interrupt events and executor digests → next turn's injected prompt section → the model's exception handling. The executor never invents vocabulary: predicates, inputs, legend and limits all come from the adapter's `bodyDeclaration` (`packages/contracts/src/body.ts`), validated at load — this is the LLM-Modulo pattern of generation plus an external sound validator ([arXiv:2402.01817](https://arxiv.org/abs/2402.01817)).

**Timescale ownership (explicit):**

- **Adapter tier — instant (one game tick).** `until: { arrive | blockedMs | monsterWithin | warped }` + `fastState` execute inside the game process; the world is the tripwire (Brooks' "the world is its own best model", [subsumption architecture](https://en.wikipedia.org/wiki/Subsumption_architecture)). Not new code — the body protocol already ships it (`bodyTaskSchema`, comment: "reflexes").
- **Executor tier — ~100–250 ms poll.** A fixed interpreter in the plugin process (where `navigation.ts` lives today): evaluates the active directive set top-down by priority, lets the winner compose macro steps (A* legs, slot/press sequences) into body tasks, and re-checks the goal gate and permissions every poll.
- **Model tier — seconds per turn.** DSH turns: goals, decomposition, skill selection, *authoring* (drafting/editing directives and skills), and everything the digests escalate as an exception.
- **Permission tier — continuous.** DSH goal state (seam 5) gates productive directives; pause (`session/cancel`) cancels the body task and disarms productive directives; protective directives degrade to "stop / step away".

**"Plant and water the parsnips."**

1. Player words → plugin feeds a DSH goal (seam 5). Goal round starts; `agent/pre-step` (seam 3) injects a body-status section plus the *skill index* — names, one-line purposes, parameters (seam 2).
2. Model turn (seconds, 1–2 calls): `world_find(kind: "dirt")` to fix the plot rect, `body_controls`/`world_observe` for toolbar slots, then one call to `skills_bind`: skill `field-work` with `{plot: [x0,y0,x1,y1], till: Slot2, plant: {item: "Parsnip", slot: 3}, water: Slot4, goal: <goal-id>}`. If no such skill exists yet, the model *authors* it — a draft directive bundle via `skills_draft` — and the validator checks it against the declaration before it can bind. Turn ends.
3. Executor (polls, no model): per tile in the plot — A* leg with `until: { arrive }`; on arrival `press: [Slot2]` + `press: [ControllerX]` (till); pass 2 swaps `Slot3`, presses `ControllerA` (plant); pass 3 `Slot4` + `ControllerX` (water). Every poll re-checks the goal is still active. `blockedMs` twice on one leg → `detour` macro (higher priority) → resume. Stamina below threshold → pause the directive, escalate in the digest.
4. Completion: the directive self-deactivates, the digest ("field-work: 15 tilled, 15 planted, 15 watered, 2 detours") rides the next `agent/pre-step`; the model updates the DSH goal to complete. The body was never idle waiting on a model, and no new per-game product code was written — the model bound data to data.

**"Get to the ladder" (monsters + low health).**

1. Model turn: goal → `skills_bind` `reach-tile` `{target: ladder, goal: <id>}`; protective directives (`danger-flee`, `cornered-fight`) are default-on and need no model call.
2. Executor submits the walk with `until: { arrive: ladder, monsterWithin: 3 }`, `fastState: true`. A monster closes inside 3 tiles: the **adapter interrupts within one game tick** — zero model calls, zero polls even. At sim speed (`walkPxPerTick: 4`, `tilePx: 64`, 60 Hz ≈ 267 ms per tile) a monster 3 tiles out arrives in ~0.8 s; a model round-trip is seconds. This tier is not optional in the mine — the brief says so.
3. Next poll: predicates fire — `monsterWithinTiles ≤ 3 && healthPct < 35` → `danger-flee` (priority 90, interrupts all) paths away; if pathing fails while adjacent, `cornered-fight` selects the weapon slot and swings (`press: [Slot4]`, `press: [ControllerX]`; sim monsters die to one swing). Both are bounded macros; neither improvises.
4. When `noMonsterWithinTiles ≥ 6` holds for 1.5 s, `reach-tile` resumes; the goal was never ended (pause-holds semantics preserved). The interrupt (tick, predicate snapshot, outcome) rides the digest; the *next model turn* owns the exceptions: eat, retreat, or re-arm — the judgment call, not the twitch.

## How it fits the DSH seams

- **Seam 6 — body port + helper libraries (the load-bearing seam).** The fixed executor (priority scan, macro runner, goal gate, validator, logger — game-agnostic, on the order of a few hundred lines) lives in the plugin exactly where `navigation.ts`/`walk.ts` live; macros are thin compositions over them emitting `BodyInputStep[]` with `until` + `fastState`. The adapter tier (`until`/`fastState`) already exists in the contract.
- **Seam 1 — tools.** `skills_list`/`skills_inspect` (index + active bindings + recent executor events), `skills_bind` (validated binding, cancellable with the caller's turn like every body tool), `skills_draft` (model proposes a directive bundle; returns validator findings, activates nothing by itself). The model keeps full access to the raw body tools — the executor is a substrate under it, not a wall.
- **Seam 2 — prompt sections.** Per-turn body-status + skill index + executor digest (interrupts, completions, escalations since the last turn).
- **Seam 3 — turn-flow hooks.** `agent/pre-step` injects that section; goal rounds reconcile directive bindings with DSH goal state.
- **Seam 4 — setup callback.** Loads the skill library and validates every artifact against the current `bodyDeclaration`; unknown input id, legend char or macro name is a loud load error (never a silent local fallback — repo rule).
- **Seam 5 — DSH goals.** The model creates/updates goals through DSH as today; the plugin *observes* goal state to gate productive directives (the anti-unattended-farming latch), and goal completion deactivates bound directives.
- **Seam 7 — local files.** `skills/<game>/<skill-id>.json` (player-readable, diffable directive bundles), `skills/<game>/<skill-id>.code.ts` in the exceptional reviewed-code case, `executor-log.jsonl` (tick, predicate snapshot, winner, macro, outcome) — next to the memory ledger under the bridge directory.
- **Side runtime? No — with one honest exception.** The interpreter is a timer in the existing Cordis plugin process; no second process, no daemon, no training loop. The exception: if a skill ever genuinely needs novel *code* (a motion primitive the macro library lacks), it must run through a DSH-provided code-execution tool contract with an inspectable interface — framed exactly as the brief allows ("a separate tool the plugin calls") — and defaults to off, mirroring how Mindcraft gates its `newAction` LLM-code capability behind `allow_insecure_coding` (off by default; [Mindcraft README](https://raw.githubusercontent.com/mindcraft-bots/mindcraft/develop/README.md)). Declarative skills are the default path and need no such gate.

## Best evidence

- **KRAFTON PUBG Ally (shipped, NVIDIA ACE)** — a real co-op AI teammate built as a dual system: quantized 2B SLM "decision core" for intent/speech over "a System 1 layer, implemented as a behavior tree" handling "movement, aiming, and immediate combat responses at game tick rate"; "reflex-level actions never have to wait for the model"; defining the boundary "went into" significant engineering — the strongest industrial evidence that composition is the shipped shape, and that the boundary must be designed, not accreted. https://developer.nvidia.com/blog/how-krafton-built-pubg-ally-a-co-playable-character-powered-by-nvidia-ace
- **DPT-Agent (ACL 2025 main)** — first autonomous real-time *simultaneous* human-AI collaboration: FSM + code-as-policy system 1, LLM with Theory-of-Mind system 2; experiments showed System 1 or System 2 alone is insufficient — the direct empirical case for composition over any monolithic owner. https://arxiv.org/abs/2502.11882
- **CoALA (Sumers et al., TMLR)** — the framework argument: a language agent is modular memory (working/episodic/semantic/**procedural**), a structured action space, and a generalized decision cycle — i.e., a skill library and an execution process are first-class architecture, not add-ons. https://arxiv.org/abs/2309.02427
- **SwiftSage (NeurIPS 2023 spotlight)** — fast/slow arbitration (cheap policy for routine steps, LLM only on hard states) significantly outperforms SayCan, ReAct and Reflexion on 30 ScienceWorld tasks — layering beats better prompting of a single layer. https://arxiv.org/abs/2305.17390
- **Voyager (Wang et al., 2023)** — an LLM-authored skill library of executable, compositional code yields 3.3x more unique items, unlocks tech-tree milestones up to 15.3x faster than prior SOTA, and the library *transfers to a new Minecraft world* to solve novel tasks — the strongest evidence that accumulated procedural memory, authored by the model, is the per-game competence engine. https://arxiv.org/abs/2305.16291
- **LLM-Modulo (Kambhampati et al., ICML 2024)** — autoregressive LLMs "cannot, by themselves, do planning or self-verification"; the working pattern is LLM generation + **external sound validation** in a bi-directional loop — exactly the `skills_draft` → validator → bind flow, and the reason LLM-authored skills are trustworthy here. https://arxiv.org/abs/2402.01817
- **Mindcraft `modes.js` (open source)** — the existence proof that a priority-ordered, interrupt-carrying reflex layer under the LLM loop is what a real community bot ships; interrupted actions come back to the LLM as auto-messages. https://raw.githubusercontent.com/mindcraft-bots/mindcraft/develop/src/agent/modes.js

## Extensibility across games

The judge's top criterion, head-on. The design splits everything into **one universal engine + per-game data**, and — crucially — makes the per-game data *model-authorable*:

- **Universal (written once, shipped once, tested once):** the executor interpreter, the macro library (A* legs, slot/press, path-away, detour — compositions over the port, not over Stardew), the validator, the tools (`skills_*` plus today's body tools), the prompt sections, the digest format, the logging schema. None of it mentions Stardew.
- **Per-game (data, not logic):** (a) the adapter declaration — which already exists per game by contract (`bodyDeclaration`: inputs with roles, legend, state fields, limits); (b) the skill library — directive bundles whose predicates and macros are assembled *from that declaration's vocabulary*. Porting to `toy2` (different state/input vocabulary) is: new declaration + one new directive pack + possibly one macro. The setup callback cross-validates, so a wrong port fails at load with a named error, not in play.
- **Who authors the per-game parts:** the model does, under validation — hand it `skills_list` + the new game's declaration and it drafts the directive pack; the validator checks the closed vocabulary; the bench's keyless sim (or a recorded replay of the new game's adapter) smoke-tests it before activation; a human reviews the diff like a small PR for the first games. This is the LLM-Modulo division: the LLM is the universal approximate knowledge source; correctness comes from the external validator. Voyager's transfer result is the precedent for library-carried competence crossing worlds; CoALA names this layer procedural memory precisely because it is the part of the agent that is allowed to be game-specific.
- **Why this beats each rival on the same axis:** pure tool calling has zero per-game code but pays a model round-trip per surprise forever and never accumulates competence (every parsnip day is day one); hand-written BTs/FSMs pay per-game *code*; LLM-BT re-pays generation and still needs an executor; skill-libraries-as-code pay per-game code generation with a live trust surface; GOAP/HTN pay per-game domains; RL pays per-game training; model-level agents pay per-genre models. The hybrid pays per-game *validated data*, authored largely by the model itself, over an engine that amortizes like `navigation.ts` did.
- **Honest first-game cost:** the predicate combinator library, the validator, and the discipline of macro design are real up-front engineering — the same one-time engine cost every rival hides inside "write the tree / domain / trainer," paid once here instead of per game.

## Latency, trust, and debuggability

- **Latency.** Three tiers: model turn (seconds — goals, authoring, exceptions only), executor poll (~100–250 ms — directive switches, macro submissions), adapter `until` (one game tick — "monster within N tiles" stops the body inside the game process). In the mine scenario the body reacts in ~0.8 s to a monster 3 tiles out with zero tokens spent; the baseline spends a model round-trip while the body stands idle — visible to a live co-op partner. PUBG Ally reached the same conclusion for a shipped shooter and moved the whole stack on-device to buy predictable latency.
- **Trust — the hybrid makes the boundary *more* inspectable, not less.** The permission surface has exactly three leaves a player can see: the DSH goal (what it is doing and why, revocable in DSH's own UI), the skill binding (which named, readable artifact is bound to that goal, with what parameters), and the directive pack (a JSON file the player can read, diff and delete). Nothing productive runs without a live player-originated goal, re-checked every poll — revocation lands within one poll, not at the next model turn. Default-on directives are protective only (flee, unstuck, stop); they cannot farm. Versus the baseline — where permission = a stream of opaque tool calls — this is a strictly smaller and more legible surface; versus pure skill-libraries, it removes unsandboxed model-written code from the default path.
- **Debuggability — each layer logs its own decisions, and the seams make attribution possible.** DSH session logs hold every model decision (goal creation, `skills_bind`, drafts); `executor-log.jsonl` holds tick, predicate snapshot, winner, macro, outcome; the adapter's task-status `reason` ("arrived"/"blocked"/"monster"/"warped") corroborates from the game side. A misbehavior decomposes by construction: wrong goal → model tier; right goal, wrong moment → directive data (diffable JSON); right directive, wrong motion → one fixed macro (unit-testable); surprise handled late → adapter tier. Monolithic owners cannot offer this attribution because there is no seam to attribute across; here every escalation event carries the layer that produced it.

## A minimal prototype on the sim

- **Harness:** import `SimAdapter` unmodified behind a bench wrapper; add three modules — the fixed executor (priority scan + macro runner + goal gate), a validator against `SimAdapter.declaration()`, and a tiny macro library over `walkTo` + slot/press steps.
- **Data:** two skill fixtures (`field-work`: plot rect + till/plant/water passes + `detour`; `reach-tile`: target + `danger-flee`/`cornered-fight` protective directives with thresholds). Farm scenario: till/plant/water a plot. Mine scenario: reach a ladder tile with monsters and low health.
- **LLM side (system 2):** a scripted stub for determinism per TASK.md's stub rules (a real GLM call if the bench harness allows one): issue the DSH goal, one `world_find`, one `skills_bind`; receive the digest between tasks. Record which numbers come from the stub.
- **What each part does:** stub model = goals + bindings + exception replies; fixed executor = everything between bindings; library = the two JSON packs. Also exercise `skills_draft`: feed the stub a malformed draft and show the validator rejecting it at load.
- **Metrics vs the pure-tool-calling baseline:** success rate, model calls per task, wall-clock, idle ratio, stuck/recovery count, LOC by kind, and the `toy2` port (new declaration + new JSON pack; count changed lines).

## Anticipated attacks and your answers

1. **"A hybrid of everything is maintainable by no one — max lines of code, max bug surface."** The code is *not* "everything": there is exactly one fixed engine (interpreter + macros + validator), and it is smaller than any rival's per-game structure because it is written once. What other advocates write as per-game code, this design stores as validated JSON. Every rival who wins a scenario here will smuggle in at least one of these layers anyway (a tree needs an executor and authoring; a mode table needs an author; a skill library needs a runtime and a validator) — the hybrid is the only proposal that *prices* all of them instead of hiding some in prose.
2. **"Each layer alone is defended by its own advocate — what did YOU add?"** The interfaces, and one vocabulary. The single load-bearing idea is that the same adapter declaration drives the model's tools, the executor's predicates, and the validator — so there is one source of truth, and artifacts flow in one direction (drafted by system 2, validated, bound to a goal, executed by system 1, digested back). The single-layer advocates' own flagship evidence is compositional: PUBG Ally is an SLM over a behavior tree; DPT-Agent is an FSM under an LLM; Mindcraft ships modes *and* an action library *and* LLM-authored actions; Voyager's curriculum is itself a deliberative loop over an execution layer. Nobody's best evidence is actually a monolith. I added the named ownership per timescale and the validated artifact flow — the part every one of those systems reports as the hard engineering ("a significant amount of engineering effort went into defining the boundary between those two layers" — PUBG Ally).
3. **"Conflicts between layers are the hardest bugs — two brains, two sources of truth."** There is one brain per timescale and one vocabulary total. The executor cannot reference anything not in the declaration (validator-enforced at load and on every adapter upgrade — invalid directives fail loudly, never silently); the model cannot submit a task that bypasses the goal gate; interrupts are events with provenance, not silent overrides. And when layers do disagree, that disagreement is *the feature*: it is the escalation path (flee now, ask the model why later). In a monolith the same disagreement is just a wrong action.
4. **"Integration cost eats the gains."** Most of the stack already exists in this repo: the adapter tier *is* `until`/`fastState` (shipped in `body.ts`), the macro library *is* `navigation.ts`/`walk.ts` with a thin runner, the goal gate *is* seam 5, the digests *are* a prompt section. The genuinely new code is one interpreter and one validator, both game-agnostic and bench-testable on the keyless sim before touching the game. The delivery path is incremental: ship the executor with zero directives (pure baseline, unchanged), add the two protective directives for the mine, then the first farm skill — each step is a small, reviewable diff under the repo's code budget.
5. **"This violates the repo's 'guide, don't script' principle — you built a behavior tree and called it data."** Head-on: the principle says fixed logic needs a stated reason the model or harness cannot do it. Two stated reasons, both in the brief: (a) reaction latency — a monster 3 tiles out arrives in ~0.8 s at sim speed while a model round-trip is seconds, so continuous survival between turns is something the *harness cadence* cannot do; (b) the executor's *content* is not product fixed logic at all — directives are model-authored, validated, inspectable data the model composes and re-composes, which is the principle's "guide" applied to execution rather than only to prompts. What remains genuinely fixed (the interpreter, protective macros) is boundary, not behavior — the same class as `walkTo`'s A*, which the repo already ships as a helper.
6. **"LLM-authored directives are just the LLM-BT advocate's trees; validation won't catch semantic errors."** The validator catches vocabulary and contract errors (unknown button, bad predicate, unreachable macro); semantics are bounded three ways — macros are a closed set of motion primitives, tasks carry step/tick limits and cancellation by construction, and every failure surfaces as an escalation event to system 2, which owns exceptions. A wrong-but-well-formed directive can waste a goal round; it cannot brick the loop, escape the permission gate, or run unbounded — the failure envelope is the actual difference from LLM-authored control flow.
